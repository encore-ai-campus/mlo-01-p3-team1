# 03. 날씨 저장 구조

- 수정일: 2026-10-13
- 프로젝트 적용 결정: 같은 네트워크의 로컬 Kafka/Spark 클러스터에서 새 날씨 파이프라인을 구현하고 최종 AWS로 이전합니다. 원문은 로컬과 S3에 함께 보관합니다. S3 실패 재시도·해시/사본 상태·보관/재처리 상세는 [최신 구현 가이드](../../product/3차_구현_결정과_익명문맥_원문보관_가이드.md)를 따릅니다.
- 화면은 날씨 패널만 유지하며 별도 강수 카드/X/닫기 상태는 제거합니다. 2026-10-14 수령음악문서우선으로PTY4/5는비점수·6은비·눈점수·7은눈점수입니다. 원래표시현상/코드를보존하며혼합최초speed 기준만미정입니다. Gemini 재설정도 서버의 같은 적격 기준을 따릅니다. 원본 PTY 표현은 보존합니다.
- 아래 기존 로컬 시험 코드/경로/수치 설명은 인계 출처의 이력입니다. 현재 저장소에 코드가 구현됐거나 AWS/S3 업로드가 완료됐다는 뜻은 아닙니다.

운영 아키텍처: MongoDB 컬렉션 + S3 파일 저장소 + Elasticsearch 조회.
현재 로컬 DB 이름은 `project3_weather_test`, ES 인덱스는 `weather-current-v1-test`.
S3 업로드·운영 서버 적용은 인프라 연결 범위. 현재 원문은 project3 내부 gzip 파일.

## 저장 대상

| 위치 | 내용 |
|---|---|
| pipeline/mapping.json | 읍면동·상위 지역 공식 코드와 대표 좌표 |
| dashboard/regions.json | 시도·시군구·읍면동·리 검색 목록, 날씨 격자 연결 |
| dashboard/road_addresses.sqlite3 | 공식 도로명주소 → 행정동 → nx·ny. 로컬 검색용 |
| 회차별 raw 폴더 | 성공한 API 원문 gzip. 압축 해제 시 원래 바이트 |
| MongoDB bronze_weather_events | 수집 이벤트 메타·원문 참조 |
| MongoDB silver_weather_history | 발표별 정제 이력 |
| MongoDB weather_latest_values | 대상 시각·항목별 최신 발표 값 |
| ES weather-current-v1-test | 격자별 최신 실황·6시간 예보·보완값 |

Bronze·Silver는 처리 단계 이름. MongoDB 정제 데이터를 Delta 파일이라고 부르지 않기.
원본 파일까지 함께 보관해야 재처리 가능.

## 주요 필드와 키

| 대상 | 한 건의 기준 / 주요 필드 |
|---|---|
| Bronze | _id=event_id, source, category, issued_at, target_at, received_at, raw_path, reading_count |
| Silver | nx, ny, kind, category, measurement, 시각, source_hash, rule_version, mapping_version, spatial_basis |
| 최신 슬롯 | 출처·종류·대상 시각·격자·항목. Silver 필드 + history_id |
| ES 문서 | _id=nx_ny, observation, forecast, base_complete, supplements_pending |

원문 연결: source_hash는 SHA256, raw_path는 원문 위치, run_id는 수집 회차.
KIM 추가 필드: query_lat·query_lon 대표점, source_ix·source_iy·source_lat·source_lon 모델 격자, spatial_distance_km 거리.
실제 수집은 data_mode=live, 원본 재생은 replay로 구분.

Silver 이력 ID: 출처+종류+발표+대상+nx·ny+항목+원문 해시+정제 버전.
KIM은 매핑 버전·좌표 선택 방식도 포함. 기본 정제 normalize_v2, 구름량 normalize_v3.
최신 슬롯 ID는 발표·해시·규칙 버전을 제외해 고정.

## 저장·최신 선택

같은 원문 재전송은 같은 ID로 처리. 이력 중복 추가 없음.
발표가 바뀌거나 원문 내용이 수정되면 별도 이력 보존.
14시 발표의 17시 예보 20℃와 15시 발표의 17시 예보 19℃는 둘 다 보관, 최신은 19℃.

최신 비교: 발표 → 수신 → 해시. 같은 발표·원문은 높은 정제 버전 우선.
최신 발표가 결측이면 결측 상태 그대로 기록. 최근 정상값으로 임의 대체하지 않기.
MongoDB 이력 → 최신 슬롯 → ES 순서. 현재 단일 Spark writer 사용.

인덱스: Silver(nx, ny, target_at, source), 최신 슬롯(nx, ny). _id는 중복 식별.
ES의 observation·forecast 내부는 조회 문서로 보관. 내부 항목 조건 검색용 매핑은 현재 범위 외.

## 도로명주소 조회 DB

로컬 SQLite 약 926MB. 날씨 수집 때마다 복제하는 데이터가 아닌 주소 기준표 한 벌.
road: 도로명코드·시도·시군구·읍면·도로명·검색문자열.
road_address: 공식 주소관리번호·road_id·건물본번/부번·지하 여부·행정동 코드/이름·날씨 지역코드·nx·ny·연결 상태.
metadata: 출처·자료 월·기상청 매핑 버전·행 수.
주소관리번호 유일 인덱스, (road_id, 건물본번, 건물부번) 조회 인덱스. 서버는 읽기 전용 접근.
운영 주소 DB 제품·배치는 인프라 연결 시 확정. 현재 MongoDB 날씨 컬렉션과 분리.

## 서비스·ML 사용

서비스는 ES 최신 묶음 조회. 음악 추천·대시보드는 이 자료를 입력으로 사용.
ML은 발표 당시 예보와 이후 관측을 같은 격자·대상 시각으로 연결.
같은 원문은 적용 정제 버전 기준으로 선택. 과거 시점 이후 발표·수신된 정보 사용 금지.
replay 수신 시각은 과거 실제 수신 시각으로 사용하지 않기.
