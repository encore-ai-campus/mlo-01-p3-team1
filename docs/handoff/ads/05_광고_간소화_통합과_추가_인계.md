# 3차 카페 광고 간소화 — 통합·추가 인계

- 작성일: 2026-10-14
- 수정일: 2026-10-15
- 기준: 사용자 수령 [간소화 원문](./04_광고_관리_간소화_인수인계서.md), 데이터 계약 `phase3-ads-data-20261014.3`
- 상태: 2026-10-15 사용자 확정 정책과 광고 서버 구현 연결입니다. 실제 공유 환경·5분 반복 기동·브라우저·운영 검증은 별도입니다.
- 범위 결정: 3차 광고는 카페 전용입니다. 업종 선택·태그 지정·업종별 매칭은 4차 확장으로 분리합니다. 수령 원문은 원문 보존용이며 3차 범위는 본 문서와 [4차 업종 매칭 가이드](./06_4차_광고_업종매칭_확장_가이드.md)를 따릅니다.

## 1. 구현 순서와 범위

간소화 원문의 관리 → 공개/측정 → 주기 집계/예산 순서는 유지합니다. 3차 범위에서 광고 대상은 카페로 고정하며, 단계별 태스크 ID와 직접 선행 관계도 유지합니다.

| 단계 | 구현/검증 | 완료로 볼 수 없는 범위 |
|---|---|---|
| 첫 관리 | `ads`, `ad_assets`, `ad_admin_changes` 세 컬렉션·MongoDB 이미지 Binary·등록/수정/중단·목록/필터/미리보기·멱등/동시성/감사·로그 전달 연결 | 공개 제공·실제 측정·토큰/예산 집계 |
| 공개/측정 | 카페 광고의 위치·기간·게시 상태·소재·검증 예산 자격, priority, 위치별 동률 순환·30분 delivery·중단3초·측정 원자 저장 | 실제 공개 화면·공유 guest·운영 검증은 별도 |
| 집계/예산 | 최초 판정/예상 항목 원자 저장·5분 통계/예산 검증·소진 이후 제공 차단·로그 복구 | 반복 작업 상시 기동·실제 결제·구매·환불 완료 아님 |
| 4차 별도 확장 | 업종 선택·관리 태그·업종별 광고 매칭/순환 | 3차 API·DB·화면·수용 기준의 선행 조건 아님 |

미연결 통계는 `연동 대기`이며0으로 꾸미지 않습니다. 연결 후 실제0과 미연결을 구분하고 집계 범위·기준 시각·지연 상태를 표시합니다. 실시간 대시보드는 요구하지 않습니다.

### 1.1. 2026-10-15 사용자 확정

- delivery의 표시 가능 수명은 발급 후30분과 광고 종료 중 이른 시각입니다. `display_expires_at`과 보고 마감 `event_expires_at`을 분리하며 보고 마감은 표시 마감+300초입니다. 실제 발생은 표시 가능 구간 안이어야 하고 수신 지연도300초 이내여야 합니다. 30분은 배달 재발급 경계이며 광고 캠페인 자체의 종료가 아닙니다.
- 제목·이미지·링크가 바뀌면 새 creative_version을 발급하고 옛 배달의 새 표시·변경 이후 발생을 차단합니다. 변경 전 유효 발생은 당시 snapshot으로300초 지연 검사를 하며, 기존 event_id 재전송은 최초 응답을 보존합니다. 위치·기간도 서버에서 별도로 검사합니다.
- 관리 통계와 예산 검증은5분 주기입니다. 배치가 인정 예상 원장 합계를 확인해 일일 또는 전체 한도 이상이면 최초 소진 확인 시각을 고정합니다. 그 시각부터 신규 발급·기존 배달 재확인·이미지 제공을 차단하고 기존 최대3초 표시 lease로 열린 화면을 숨깁니다.
- 검증 시각보다 **이전에** 발생한 유효 보고는300초 이내 수신 시 초과분도 인정합니다. 시각과 같거나 이후 발생은 제외합니다. 예약량 확보나 잔여23/20토큰 조건을 사용하지 않으며 검증 사이의 초과에 전역 고정 상한은 없습니다.
- 광고 자동 종료는 예산 소진과 게시 기간 종료입니다. `paused` 수동 중단은 별도 유지하며 증액/날짜 전환으로 자동 해제하지 않습니다. 일일 집계/검증의 KST 날짜는 기존 발생일 정렬을 따르는 개발 기준이며 별도 사용자 금액/경계 승인으로 표시하지 않습니다. `cap_at_midnight=False`를 기본으로 배달을 자정에 강제 단축하지 않습니다.

실제 예산액은 광고 관리 API로 입력합니다. 제목100자·priority100·미사용 이미지7일은 승인되지 않은 별도 제안입니다. 업종 태그는4차로 유지합니다.

## 2. 3차 카페 전용 계약

- 3차의 모든 광고 기록은 카페 대상입니다. `targeting_mode`, `target_tag_codes`, `tag_catalog_version`, `targeting_policy_version` 등 업종/태그 입력·저장 필드는 추가하지 않습니다. 사용자가 임의로 업종 필드를 보내면 공통 strict 입력 검증으로 거부합니다.
- 사용자에게 광고용 업종 선택·설문·로그인을 요구하지 않습니다. 광고 공개 조회에 필요한 guest 문맥은 중복 방지·소유 검증용이며 업종 정보를 담거나 추천 요청 여부를 조건으로 삼지 않습니다.
- 광고는 위치·기간·paused·소재·예산 자격을 검사한 뒤 높은 `priority` 순으로 제공합니다. 같은 priority에서는 상단/하단 위치별 round-robin을 적용합니다. 업종 태그 우선이나 ALL fallback은 없습니다.
- 최초 guest 발급과 추천 미요청 상태의 집계 기준은 유지합니다. 음악 추천에 필요한 지역 입력과 광고 대상 카페를 연결하지 않습니다.
- 보존한 업종별 확장은 [4차 광고 업종 매칭 확장 가이드](./06_4차_광고_업종매칭_확장_가이드.md)에서 다룹니다. 4차 구현을 위해 별도 코드·데이터 사전·입력 UI·공개 API·순환 상태·수용 정책을 결정해야 합니다.

광고 서비스에는 검증된 외부 ID만 참조하고 비밀번호·프로필·세션/guest 원문 토큰을 복제하지 않습니다. 공개 응답에도 사용자 ID/인증 원문을 노출하지 않습니다.

## 3. 세 컬렉션과 PostgreSQL 로그 연결

이미지 원본은 `ad_assets.image_bytes`에 MongoDB Binary로 보존합니다. 정적2MB와 BSON 전체 크기를 검증하고 목록 JSON에는 바이트를 넣지 않습니다. 이미지 교체는 새 asset, 미리보기는 인증된 조회, 공개 이미지는 게시 자격을 검사하는 별도 조회 경계로 제공합니다. 실제 URL·캐시·미사용/백업 정리는 INF/B/C가 인계합니다. Django ORM으로 MongoDB를 관리하지 않고 별도 어댑터와 replica set 트랜잭션을 유지합니다.

별도 outbox 컬렉션을 첫 단계에 추가하지 않도록, 다음은 기존 공통 로그 계약을 연결하는 **기술 보완 기준**입니다. 수령 원문에 이미 확정된 필드라고 취급하지 않습니다.

- 관리 변경/멱등 성공 기록과 함께 `ad_admin_changes`에 `log_relay` 보조 객체를 같은 MongoDB 트랜잭션으로 저장합니다. `log_event_id`는 해당 `log_id`에서 안정적으로 정하고 불변 `payload`/`payload_hash`, `status=PENDING/SENT`, `attempt_count`, `next_retry_at`, `last_error`, `sent_at`을 관리합니다. 현재 relay는 조건부 claim/lease·재시도로 오래된 작업자의 ACK를 막습니다. 공유 sink/프로세스 운영은 별도 검증입니다.
- payload는 당시 관리자/광고/asset·operation·changed·시각·version·request_id·is_test와 필요한 참조입니다. 이미지 원본·개인 인증 토큰·비밀번호는 넣지 않습니다. relay 상태를 변경해도 감사 snapshot과 최초 멱등 응답을 바꾸지 않습니다.
- PostgreSQL에 `UNIQUE(log_event_id)`로 저장/동일 payload를 확인한 뒤 SENT로 표시합니다. 저장 후 표시 전 종료는 같은 ID로 재전송하며 같은 ID의 다른 payload는 경보입니다. PostgreSQL 장애 때는 pending을 유지하고 재시작 후 다시 전달합니다.
- 인증 서비스 장애는 관리 변경 차단, 로그 사본 전달 지연은 커밋된 업무 결과 유지로 구분합니다. 두 DB를 하나의 원자 트랜잭션으로 설명하지 않습니다. relay는 광고 통계/토큰을 다시 계산하지 않습니다.
- pending과 감사/멱등 보관 의무가 남은 자료는 삭제하지 않습니다. 응답 만료와 감사 보관은 구분하며 TTL만으로 참조 보호를 대신하지 않습니다.

현재는 첫 관리3개에 공개5개(`ad_rotation_state`, `ad_deliveries`, `ad_events`, `ad_repeat_windows`,
`ad_estimated_usage_ledger`)와 정책2개(`ad_budget_states`, `ad_daily_metrics`)를 추가했습니다.
공개 claim은 delivery 내부, 측정 로그는 event 내부, 최초 소진 로그는 예산 상태 내부의 log_relay입니다.
별도 claim·ad_versions·사용자·outbox 컬렉션을 만들지 않습니다. 원본 이력은 ad_admin_changes의 snapshot을 사용합니다.
관리·측정·소진 로그는 각각 relay_ads_logs·relay_ads_event_logs·relay_ads_budget_logs로 같은 durable
ADS_LOG_SINK에 전달하며 실제 PostgreSQL 연결 완료를 뜻하지 않습니다.

## 4. 주기 통계와 예산

단가8/5/클릭추가15·50%/1초·delivery각각1회·반복60/300초·지연5분·발생일KST는 유지합니다. 후속 측정에서 최초 판정과 예상 항목은 원자 저장하고 배치는 그 항목의 합계를 갱신합니다. 현재 배치는 범위 재계산/교체로 재실행 중복 합산을 막습니다. 지연/자정/90일 원본과365일 원장 보관을 검증합니다.

5분 배치는 원장 합계로 광고별 일일/전체 예산을 검증하고 통계를 대상 범위 재계산/교체로 갱신합니다.
소진 시각은 budget_version별 이력에 고정하며 지연 보고가 늘어도 뒤로 밀지 않습니다. 예산 변경은 새 버전을
생성하고 새 검증이 끝난 뒤 다시 적격을 판정합니다. 일일 검증 상태는 KST 날짜별로 두며 전체 소진은 같은
예산 버전의 날짜 전환에도 유지합니다. 과거 원장을 지우거나 새 금액/단가로 재산출하지 않습니다.

조회는 배치 검증 상태를 읽습니다. 예산 미설정 또는 검증 상태 없음은 제공 부적격이고, 검증 자료가300초를
초과해 오래되면503으로 차단합니다. 이는 배치 장애이며 새 광고 자동 종료 사유가 아닙니다. 통계는
READY/PARTIAL/PENDING·as_of·coverage·coverage_from/coverage_through·is_stale로 미연결과 실제0을 구분하고 지연/자정 보완을 포함합니다.
실제 예산액·장기 누적/보관 초과 처리·재개·이미지 정리 세부는 별도 인계입니다.

운영 정책 연결 경로는 `domains.ads.runtime_policy.get_public_policy`이며 1800초·split_deadlines=True·
check_budget_history=True·cap_at_midnight=False를 반환합니다. provider와 공유 guest·서명키·HTTPS 주소를
실제 환경 설정으로 연결해야 합니다. apply_ads_policy_schema는 기본 dry-run이며 --apply는 로컬 `_dev`만
허용합니다. refresh_ads_policy는 기본 한 번 실행하고 --watch일 때300초 시작 간격으로 반복합니다.
실제 watch·공유 PostgreSQL·AWS·공개 브라우저는 실행 검증과 구분합니다.

## 5. 추가 수용 사례와 담당

| 사례 | 기대 결과/담당 |
|---|---|
| 첫 관리 저장·이미지 변경·재전송/실패 | 세 컬렉션 원자성·기존 바이트 보존·감사/응답 일치 / B·INF |
| 위치·기간·paused·소재·예산 자격 | 부적격 광고 제외, 위치별 상위 priority 후보 제공 / B·C |
| 같은 위치·priority 동률 광고 | top/bottom별 round-robin, 중복 delivery에서 커서 미전진 / B |
| 업종/태그 관련 필드 포함 요청 | 3차 strict 입력 검증에서 거부, 업종별 자료/상태 생성 없음 / B·C |
| 미연결 통계·연결된 실제0 | `연동 대기`와0 구분 / B |
| PostgreSQL 저장 후 SENT 전 종료 | 같은 `log_event_id` 재전송·중복 로그 없음 / B·INF |
| 로그 지연·관리 인증 장애 | 전자는 pending 유지, 후자는 관리 요청 차단 / B |
| 집계 재실행·지연/자정·예산 경계 | 예상 항목 중복 없음·발생일 유지·채택 예산 모드 대조 / B·PL·INF |

이번 사용자 작업은 광고 서버 로직/API이며 관리 화면은 별도 담당자가 제작합니다. 팀 연결에서 B는 관리 API·MongoDB·감사/멱등·로그 relay·측정/집계, C는 공개 배너·카페 전용 공개 배치, INF는 독립 API/MongoDB·원본 이미지 조회·replica set/권한/복구, PL은 운영/예산 문구와 수용을 맡습니다. 실제 구현/설치/GitHub 변경 완료를 뜻하지 않습니다.
