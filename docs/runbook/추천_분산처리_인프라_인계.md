## 1. 배치와 실행 단위

기존 14대 계획을 유지하고 두 Control을 사용합니다. 사용자별 추천 작업을 여러 프로세스가 나누며, 한 선곡표의 계산을 여러 서버로 쪼개지는 않습니다.

```text
ALB ─┬─ Control A: Django ASGI API 1프로세스 ─┐
     └─ Control B: Django ASGI API 1프로세스 ─┴─ PostgreSQL Job 큐
                                                  ├─ A: rule 워커 1개
                                                  ├─ B: rule 워커 1개
                                                  └─ B: gemini 워커 1개
```

API는 요청을 저장하고 HTTP 202/job_id/poll_url을 반환합니다. 워커가 DB에서 작업을 점유하고 결과를 저장하며 브라우저는 기존 조회 API로 결과를 확인합니다. 브라우저/ALB의 연결 고정은 요구하지 않습니다. 두 API의 DB·Django SECRET_KEY·쿠키/도메인·광고 공유 인증·카탈로그가 일치해야 합니다. DB 세션은 PostgreSQL에 저장하고 프로세스 로컬 메모리를 공유 인증 저장소로 쓰지 않습니다.

| 실행 단위 | 초기 배치 | 동시성·장애 경계 |
|---|---|---|
| 공개/관리 API | A/B 각각 Uvicorn 1프로세스 | ALB가 두 호스트로 분산. 프론트 정적 자산·광고 프록시는 기존 배포 계약으로 연결. 호스트 내부 API 수 증가는 Linux/부하 검증 후 조정 |
| `--queue rule` | A/B 각각 1프로세스 | 두 추천 작업 동시 처리. 프로세스마다 heartbeat 스레드 1개 사용 |
| `--queue gemini` | B에 1프로세스 | 모든 호스트가 공통 DB의 동시 호출 1개·시작 간격 2초 제한을 사용 |
| Collector/Driver/스케줄러 | 기존 단일 active Control | 기존 ZK/fencing/checkpoint 계약 유지. 추천 워커를 이 단일 active 그룹에 묶지 않음 |
| Kafka/Spark/ES·광고/Mongo | 기존 전용 호스트 | 이번 작업은 노드·Peering·SG·날씨/광고 저장 흐름을 변경하지 않음 |

위 개수·시간·자원 제한은 첫 부하 시험을 위한 실행 예시입니다. 운영 처리량 확정값이나 Gemini 프로젝트의 실제 할당량이 아닙니다. Gemini 워커가 B 한 대에만 있으면 B 장애 동안 재설정 처리는 대기합니다. A에 예비 Gemini 워커를 추가 기동하려면 별도 ID/설정 파일을 사용하고 동일한 전역 제한을 유지합니다. A/B 모두 기동해도 공통 한도가 1이면 하나만 작업을 점유합니다. 메모리 증가와 Control 승계 후의 전체 자원 사용을 먼저 확인합니다.

## 2. 수령 원문과 현재 실행 코드의 차이

[TEAM-HANDOFF](../handoff/infra/TEAM-HANDOFF.md)·[APPLICATION-CONTRACT](../handoff/infra/APPLICATION-CONTRACT.md)는 FastAPI/ASGI와 앱 실행 계약 보완을 설명합니다. 현재 통합 코드의 API는 **Django/DRF**, 실제 ASGI 진입점은 `backend.cafe.asgi:application`입니다. 이번 작업은 이 코드를 실행하는 `uvicorn==0.54.0`을 잠금 파일에 추가했습니다. FastAPI로 전환하지 않았으며 수령 원문은 수정하지 않았습니다.

별도 앱 계약의 실제 프레임워크·명령·worker 수·의존성 lock/SHA256은 위 Django 진입점과 이번 배포 커밋으로 기록해야 합니다. 루트 `.venv`와 `backend/requirements.lock`을 사용하고 광고 가상환경/lock을 합치지 않습니다. API 호스트 8000·`/health/`는 기존 인계 규격입니다. 개발용 `runserver`를 운영 실행 명령으로 쓰지 않습니다.

## 3. 배포 전 준비

1. A/B에 **같은 코드 버전과 잠금 의존성**을 배치합니다. 경로는 `/opt/music-apps/control`, 사용자/그룹은 `control` 예시입니다. 실제 경로가 다르면 unit과 앱 실행 계약을 함께 맞춥니다.
2. A/B가 **동일한 PostgreSQL 업무 DB**에 연결되는지, CA·서버 이름 검증을 유지한 `sslmode=verify-full`인지 확인합니다. SQLite로 다중 워커를 운영하지 않습니다. PG 1대는 여전히 단일 장애 지점입니다.
3. 새 migration `recommendation/0006_distributed_dispatch`를 적용합니다. 기존 작업에 nullable 관측/호출 필드와 복구 횟수, 큐 인덱스, `DispatchControl` 테이블을 추가합니다. 음악/날씨/광고 테이블을 변환하지 않습니다.
4. 검수된 실제 카탈로그·지역/날씨 읽기 모델·공통 인증/outbox를 기존 통합 절차로 준비합니다. 합성 `seed_c_demo`나 미검수 프리뷰를 운영 데이터로 등록하지 않습니다.
5. Collector/Driver supervisor와 추천 서비스는 별도 unit으로 관리합니다. 모든 추천 워커를 Spark executor나 웹 startup hook 안에서 자동 생성하지 않습니다.

배포 시 기존 API의 새 추천 접수를 잠시 중지하고 모든 기존 추천 워커를 drain한 뒤 migration을 한 번 적용합니다. 구 워커와 새 워커를 혼합 실행하면 구 워커가 전역 Gemini 제한을 우회하므로 rolling 혼합을 허용하지 않습니다. 대기 Job과 부모 선곡표·승인·제외·피드백은 보존합니다. offset/checkpoint 초기화·DB 재생성은 하지 않습니다.

```bash
cd /opt/music-apps/control
.venv/bin/python -m pip install -r backend/requirements.lock
# 실제 비공개 환경이 주입된 셸 또는 배포 실행기에서 실행
.venv/bin/python -m backend.manage migrate --plan
.venv/bin/python -m backend.manage migrate --noinput
.venv/bin/python -m backend.manage check_runtime
.venv/bin/python -m backend.manage check_runtime --connect
```

이 명령은 인프라 담당자가 승인된 배포 구간에 실행할 절차이며 이번 코드 작업에서 운영 DB에 실행한 기록이 아닙니다. `check_runtime --connect`는 카탈로그·인증·날씨·Kafka 등 기존 서비스 준비 검사를 포함합니다. 큐 검사 통과만으로 전체 서비스를 READY로 처리하지 않습니다.

## 4. 환경 파일과 systemd 예시

실행 파일은 [설정 폴더](../../config/environments/recommendation/README.md)에 있습니다. 실제 비밀값은 Git에 넣지 않습니다.

| 호스트 파일 | 내용 |
|---|---|
| `/etc/music-cluster/control/database.env` | 기존 인프라 PG 설정. 앱이 읽는 이름 `PGHOST/PGPORT/PGDATABASE/PGUSER/PGPASSWORD/PGSSLMODE/PGSSLROOTCERT`로 인계 |
| `/etc/music-cluster/control/application.env` | `DJANGO_SECRET_KEY`·허용 호스트/CSRF origin·공통 인증·날씨/피드백/광고 어댑터 등 기존 앱 설정 |
| `/etc/music-cluster/control/recommendation.env` | `shared.env.example`의 큐/탐색/호출 한도. API_BIND_HOST만 호스트별 정확한 사설 IP로 설정 |
| A: `recommendation-rule-1.env` | `control-a-rule.env.example`: queue=rule, 고유 worker ID |
| B: `recommendation-rule-1.env` | `control-b-rule.env.example`: queue=rule, 고유 worker ID |
| B: `recommendation-gemini-1.env` | `control-b-gemini.env.example`: queue=gemini, 고유 worker ID와 실제 Gemini 키 |

파일은 root 소유·control 그룹 읽기 `0640`, 상위 디렉터리는 승인된 접근 권한으로 준비합니다. A/B의 dispatch 한도·Gemini 모델/프로젝트/할당량이 일치해야 합니다. 제한은 이 앱의 같은 PG DB를 쓰는 워커끼리 공유하며 다른 DB나 다른 앱의 키 사용량까지 통제하지 않습니다. `backend/.env`도 지원하지만 프로세스 환경이 우선합니다. 이 예시들은 자동 복사·자동 활성화되지 않습니다.

unit의 초기 자원 예시는 API 전체 1GiB/CPUQuota 100%, 추천 워커당 2GiB/CPUQuota 100%입니다. `CPUQuota=100%`는 호스트 전체가 아니라 CPU 1개 분량의 상한입니다. 시스템·Collector/Driver·추가 Gemini 워커까지 합산해 8GiB Control 안에서 측정합니다. MemoryMax에 도달하면 OOM으로 워커가 종료될 수 있으므로 `OOMKilled/MemoryCurrent/CPUUsageNSec`와 재시작 횟수를 확인하고 실제 카탈로그 기준으로 조정합니다. T3 Standard의 CPU credit도 관측합니다.

```bash
# 환경 파일을 채우고 배포 경로/권한/메모리 예산을 확인한 뒤
sudo install -m 0644 config/environments/recommendation/music-recommendation@.service /etc/systemd/system/
sudo install -m 0644 config/environments/recommendation/music-recommendation-api.service /etc/systemd/system/
sudo systemd-analyze verify /etc/systemd/system/music-recommendation@.service /etc/systemd/system/music-recommendation-api.service
sudo systemctl daemon-reload
# 양쪽 Control
sudo systemctl enable --now music-recommendation-api.service music-recommendation@rule-1.service
# 초기에는 B에서만
sudo systemctl enable --now music-recommendation@gemini-1.service
```

API 예시는 사설 IP bind·`--no-proxy-headers`이며 전달 헤더를 임의 신뢰하지 않습니다. 실제 ALB HTTPS 종료와 Django의 신뢰 프록시/HTTPS 인식·CSRF·SSO는 기존 [SSO 인계](../../config/environments/sso/README.md) 및 인프라 ingress 제한에 맞춰 별도 수용 검증합니다. 이 템플릿만으로 공개 HTTPS/SSO 연결 완료를 표시하지 않습니다. `/health/` 200과 ALB target 두 개의 healthy를 모두 확인합니다.

## 5. 공유 설정의 의미

| 설정 | 예시 | 동작 |
|---|---:|---|
| `RECOMMENDATION_QUEUE` | rule / gemini | 프로세스가 점유할 작업 종류. all은 기존 단일 워커 호환 모드이며 rule 우선 |
| `RECOMMENDATION_WORKER_ID` | control-a:rule-1 | 최대160자 ASCII 영문·숫자·`_.:-`. 미지정 시 hostname/PID/queue 조합 |
| `RECOMMENDATION_LEASE_SECONDS` | 30초 | DB 시각 기준 작업 임대 |
| `RECOMMENDATION_HEARTBEAT_SECONDS` | 10초 | lease 절반 미만. heartbeat 스레드가 갱신하며 무한 연장은 하지 않음 |
| `RECOMMENDATION_JOB_TIMEOUT_SECONDS` | 180초 | 한 점유의 lease 연장 상한. 실행 중 계산을 즉시 강제 중단하는 CPU 타이머는 아니며 만료 후 결과 저장을 차단 |
| `RECOMMENDATION_MAX_RECOVERIES` | 2회 | 최초 실행 뒤 자동 회수 횟수. 외부 호출 시작 후의 불확실한 Gemini 작업은 회수·재호출하지 않음 |
| `RECOMMENDATION_MAX_QUEUED_RULE/GEMINI` | 100 / 20 | 대기 중 작업 수 상한. API의 DB 트랜잭션에서 종류별 동시 검사 |
| `GEMINI_MAX_CONCURRENT` | 1 | 전 호스트의 Gemini 점유/미확정 호출 예약 상한 |
| `GEMINI_MIN_INTERVAL_SECONDS` | 2초 | 호출 예약 시작 사이의 최소 간격. 실제 계정의 RPM/TPM/일 한도를 대신하지 않음 |
| `GEMINI_TIMEOUT_MS` | 60000ms | SDK 호출 한도. 작업 timeout보다 짧아야 함 |
| `RECOMMENDATION_WORKER_IDLE_SECONDS` | 1초 | 작업이 없거나 제한 중인 워커의 다음 조회 간격 |

기본 추천은 기존 점수·필터·시간·확장 알고리즘을 그대로 실행합니다. 지역 없음=OFF, OFF 날씨 독립, ON 예보 검증, Gemini 신규곡 20% 내림값과 부모 보존도 유지합니다. 새 큐가 `CANDIDATE_SHORTAGE`를 만드는 것은 아닙니다.

대기열이 가득 차면 신규 요청에 HTTP 503 / `RECOMMENDATION_QUEUE_FULL`과 재시도 안내를 반환합니다. 요청에서 생성하려던 Family/Job/이벤트·멱등 응답은 같은 트랜잭션에서 롤백합니다. 클라이언트는 나중에 같은 멱등키로 재시도할 수 있습니다. 접수된 작업은 기존 202/폴링 계약을 유지합니다.

## 6. 종료·중단·재시작

일반 `systemctl stop`의 SIGTERM은 새 작업 점유를 멈추고 현재 작업의 완료를 기다립니다. unit의 종료 대기 예시는 210초입니다. 준비/탐색/호출의 실제 최악 시간을 측정해 조정합니다. heartbeat 스레드가 사라지거나 강제 종료되면 lease 만료 뒤 다른 워커가 회수할 수 있으며, 이전 token/generation의 결과/실패 갱신은 거부합니다. Playlist의 Job 1:1 제약도 유지합니다.

Gemini 호출 시작 전에 DB에 provider_attempted와 예약 만료를 기록합니다. 정상 응답을 확인하면 호출 예약을 해제합니다. timeout·프로세스 중단 등 불확실한 호출은 자동 재호출하지 않으며 `PROVIDER_OUTCOME_UNKNOWN` 또는 당시 provider 오류로 종료합니다. 남은 호출 예약은 SDK timeout+lease 유예(예시90초)까지 유지합니다. 이는 로컬 앱의 중복 호출을 보수적으로 제한하는 장치이며 외부 제공자가 요청을 실제 취소했거나 과금하지 않았음을 보장하지 않습니다. 운영자가 제공자 기록을 확인한 후 사용자가 새 재설정을 명시 요청해야 합니다. 예약/상태를 수동 SQL로 초기화해 강제로 재호출하지 않습니다.

[Control fencing 원문](../handoff/infra/CONTROL-FENCING.md)은 이전 Control EC2 전체를 중지할 수 있습니다. 해당 호스트의 API와 추천 워커도 함께 중단됩니다. ALB가 살아 있는 API로 전환하고 PG 큐를 다른 추천 워커가 회수하는지 시험해야 합니다. 이 추천 큐의 동시 처리와 Spark Driver의 단일 writer/fencing은 별도 계약입니다. PostgreSQL이 중단되면 작업 접수·선점·호출 예약도 중단하며 프로세스 로컬 큐나 로컬 호출 한도로 우회하지 않습니다.

## 7. 관측과 수용 기준

```bash
cd /opt/music-apps/control
.venv/bin/python -m backend.manage check_recommendations --max-wait-seconds 60
sudo systemctl show music-recommendation@rule-1.service -p ActiveState -p NRestarts -p MemoryCurrent -p CPUUsageNSec
sudo journalctl -u music-recommendation@rule-1.service --since '10 minutes ago'
```

`check_recommendations`는 DB를 읽기만 합니다. 큐별 상태 수·가장 오래된 대기·만료 lease·호출 예약·실행 worker ID를 반환합니다. 최근 완료100건의 실행 P95는 성공/실패가 섞인 관측치이며 대기 포함 사용자 응답 P95가 아닙니다. 작업을 claim하거나 Gemini를 호출하지 않습니다. `worker_liveness_verified=false`를 항상 반환하므로 대기가 없다는 이유로 워커가 살아 있다고 판단하지 않습니다. 실제 서비스 상태와 함께 확인합니다. 만료 lease 또는 지정 대기 임계 초과는 ATTENTION/종료코드1입니다.

작업 로그는 job_id·method·worker_id·generation·대기/실행/CPU 시간·최종 상태를 기록합니다. 입력 조건·부모 snapshot·키·DB DSN·외부 오류 본문은 로그에 출력하지 않습니다. 기존 운영/로그 대시보드에 이 기록을 연결하는 작업은 INF의 수집/보관 계약으로 진행합니다.

실제 연결 후 다음을 수행합니다.

1. 서로 다른 익명 문맥에서 OFF 추천을 동시에 요청해 A/B의 서로 다른 worker_id와 성공 결과를 확인합니다. ON도 실제 유효 예보로 반복합니다. 타 문맥 결과 조회가 차단되고 기존 부모/평가/승인 상태가 유지되는지 확인합니다.
2. 격리 시험 환경에서 Gemini 요청을 동시에 보내 동시 예약 상한과 시작 간격을 확인하고, 그동안 rule 추천이 진행되는지 확인합니다. 실제 키·비용을 쓰는 시험은 별도 실행 승인을 받습니다.
3. 격리 환경에서 rule 워커를 강제 종료해 lease 만료 회수와 결과 단일 저장을 확인합니다. Gemini 외부 호출 후 중단은 자동 재호출되지 않아야 합니다. 운영 데이터에서 강제 중단 시험을 수행하지 않습니다.
4. 동시 생성1→2→5→10건 등으로 늘려 접수/대기/완료 P50·P95, 성공/부족/탐색 미완료, CPU·메모리 peak·PG 연결/락·T3 credit을 기록합니다. 작은 고정 자료의 통과를 실제86,485곡 카탈로그 처리량으로 환산하지 않습니다.
5. 예고한 큐 상한에서 접수 거절/나중 재시도와 신규 접수 재개를 확인합니다. 과부하를 후보 부족으로 표시하지 않습니다.
6. 단일 Control 상실 후 API 건강 상태·추천 회수·남은 Control의 메모리·Gemini 예비 기동을 확인합니다. PG/Mongo 단일 노드의 장애 복구 목표는 별도로 검증합니다.

운영 동시 이용자 수·P95 목표 달성·Linux 자원 한도 적합·ALB/HTTPS/SSO·실제 날씨·실제 Gemini·실제 fencing 검증은 아직 완료 항목이 아닙니다. 워커 수를 늘릴 때는 DB 최대 연결 수와 heartbeat 연결도 합산합니다. 반복 부하에서 Control의 CPU/메모리가 부족하면 추천 워커 전용 호스트 분리를 별도로 검토하며 기존 14대를 자동 증설하지 않습니다.

## 8. 코드 회귀 검사 재실행

```bash
# 격리된 PostgreSQL 시험 DB 설정과 DJANGO_SECRET_KEY가 주입된 환경
python -m backend.manage test backend.recommendation.tests.test_dispatch --noinput --verbosity 2
python -m backend.manage makemigrations --check --dry-run
python scripts/check_routing.py
```

PostgreSQL 전용 검사는 독립 세션 경합과 독립 프로세스 두 개의 실제 규칙 선곡/단일 결과 저장을 포함합니다. 테스트용 고정 자료를 사용하며 실제 Gemini 네트워크 호출은 하지 않습니다. SQLite 실행에서는 PostgreSQL 전용 검사가 skip되므로 이를 분산 처리 통과 근거로 사용하지 않습니다. 최종 명령·결과는 [변경 라우팅의 검증](../development/추천_분산처리_변경_라우팅.md#검증과-인계-상태)에 기록합니다.
