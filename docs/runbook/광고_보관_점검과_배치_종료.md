# 광고 보관 점검과 배치 종료

- 작성일: 2026-10-16
- 수정일: 2026-10-16
- 연결 작업: AD-02/AD-05/AD-06·I-03·Q-03의 광고 저장/배치 검증. 기존 ID·선행·담당 배정은 유지합니다.
- 범위: 기존 확정 보관 기준의 읽기 점검과 정책 작업의 안전한 종료·재시작 검증입니다. 공유 인증은 사용자 답변대로 규격 수령 대기입니다.

## 1. 보관 점검

`ad-server/backend`에서 광고 MongoDB 설정을 확인한 뒤 실행합니다.

```powershell
.\.venv\Scripts\python.exe manage.py check_ads_retention --limit 100
```

명령은 primary를 확인하고 서버의 `ADS_IS_TEST` 범위만 조회합니다. `--limit`은 컬렉션별1~1000문서이며 기본100입니다. `_id` 오름차순의 제한 표본을 검사하므로 큰 DB에서 기간 도래 자료를 전수 발견한다는 뜻은 아닙니다. `total`은 전체 건수, 나머지 `sample_` 값은 표본 결과입니다. 여러 쿼리 사이의 동시 변경을 고정하지 않으므로 `snapshot_consistent=false`입니다.

| 컬렉션 | 기존 보관 기산점 |
|---|---|
| ad_events | 최초 서버 received_at +90일 |
| ad_deliveries | last_used_at과 last_received_at 중 늦은 시각 +90일. 단순 재전송으로 값을 갱신하지 않는 기존 계약 유지 |
| ad_admin_changes | 실제 변경의 occurred_at +365일. changed=false 기록은 보관 세부 미정으로 분리 |
| ad_estimated_usage_ledger | 최초 processed_at +365일 |
| ad_daily_metrics | 해당 metric_date_kst 다음 KST 자정 +365일. 최신 as_of로 기간을 연장하지 않음 |

기간이 도래하면 `REVIEW_DUE`, 기간 안이면 `WITHIN_RETENTION`, 무변경 관리 기록은 `POLICY_PENDING`입니다. 기준 시각/날짜가 없거나 잘못되면 `INVALID_BASIS`로 기록하고 전체 상태 `INVALID_DATA`·실패 종료코드로 알립니다. 미래 서버 시각도 확인 대상입니다. 다른 정상 결과는 `REVIEW_READY`입니다.

기간 도래 표본은 현재 광고·공유 asset·delivery 이력·event/원장·예산 이력과 열린 보고 기한을 읽기 조회합니다. 참조가 있으면 `sample_reference_observations`와 `sample_due_with_references`에 표시합니다. 이는 연결 존재에 대한 관측이며 새 보관 연장 정책이나 최종 삭제 금지/허용 판정이 아닙니다. 현재 자료를 기준으로 과거 판정을 다시 계산하지 않습니다.

`ads`, `ad_assets`, `ad_budget_states`, `ad_rotation_state`, `ad_repeat_windows`는 현재 서비스 상태 또는 보관/정리 세부 미정으로 제외합니다. 이미지 원본·사용자/쿠키·로그 payload를 읽어 출력하지 않습니다. 식별자와 실제 접속 URI도 결과에 출력하지 않습니다.

**이 명령에는 삭제·TTL 설정·retention_due_at 갱신·--apply 모드가 없습니다.** `deletion_allowed=false`를 반환합니다. 이미지/백업·장기 누적·무변경 멱등 기록·최초 소진 이력의 세부 보관과 참조 보호 삭제는 PL/B/INF 후속입니다. 같은 업무 문서의 log_record와 이전 log_relay도 변경하지 않습니다. 기준은 [ADS 저장/보관](../handoff/ads/02_광고_MongoDB_저장과_로그_연결.md)과 [광고 로그 계약](../development/ads/MongoDB_광고_로그_저장_계약.md)입니다.

## 2. 정책 작업의 종료와 재시작

```powershell
# 단발: 결과와 실패 종료코드 확인
.\.venv\Scripts\python.exe manage.py run_ads_workers
# 반복: 기존300초 주기를 유지하고 오류 후 다음 주기에 재시도
.\.venv\Scripts\python.exe manage.py run_ads_workers --watch
```

watch는 시작 상태를 즉시 출력하고 이후30초 간격으로 현재 작업 상태를 출력합니다. 초기 `RUNNING`은 성공 확인이 아닙니다. 작업 성공/오류는 상태의 마지막 시작·완료·성공 시각과 구분합니다. 오류에는 안전한 종류/코드만 남깁니다.

Ctrl+C 또는 메인 스레드의 SIGTERM 요청은 새 반복을 중단하고 실행 중인 작업의 종료를 최대10초 기다립니다. 기다린 뒤에도 남으면 실패로 알립니다. 기존 SIGTERM 핸들러는 종료/오류 후 복원합니다. 메인 스레드가 아닌 실행에서는 프로세스 신호 핸들러를 바꾸지 않습니다. 강제 종료·호스트 장애·Windows 강제 프로세스 종료까지 같은 동작이라고 주장하지 않습니다.

재실행은 같은 원장 범위를 재계산·교체하므로 일별 지표를 중복 더하지 않습니다. 광고/관리 로그·cutoff·최초 판정/원응답은 보존합니다. 이 종료 지원이 systemd 설치나 실제 Linux 신호 수용 완료를 뜻하지 않습니다. INF는 실제 호스트에서 서비스 기동/종료·제한 시간·재시작 정책·경보를 검증해야 합니다.

## 3. 이번 검증과 인계

2026-10-16 단위/API367개와 별도 전용 MongoDB replica set의41개 시험이 통과했습니다. 추가 시험은90/365일 경계·KST 기산점·무변경 미정·표본 제한·읽기 전용·참조/환경 분리, 신호/키보드 종료 분기와 오류 후 핸들러 복원을 다룹니다.

실제 DB에서는 원본/로그/이미지/인덱스 불변을 확인했습니다. 별도의 연결 실패를 발생시킨 작업자를 중단한 뒤 정상 저장소로 두 번 재시작해 ERROR→OK 복구·집계 한 행 유지·로그/원장 불변을 검증했습니다. 정상 운영300초 주기 장기 관측, 실제 Linux SIGTERM 전송과 AWS/백업 복원은 미실행입니다.

기존 로컬27019 포트는 시험 시 요구 replica set 조건과 맞지 않았으므로 변경하지 않았습니다. 별도 포트/디렉터리의 임시 시험 프로세스만 생성·종료했고, 공유/운영 DB는 변경하지 않았습니다. 실제 실행 기록과 문서 검사 결과는 [광고 검증 기록](../acceptance/광고_개발_준비_검증.md)의 최신 절을 따릅니다.

다음 연결은 [남은 작업](../development/ads/광고_남은_작업과_연결_계획.md)의 공유 인증·정식 화면·운영 인프라입니다. 인증 담당자는 `AdminIdentity(account_id, identity_source, role, active, ads_allowed)`와 `PublicGuestContext(owner_guest_id, measurement_available, response_finalizer)`를 반환하는 서버 어댑터의 실제 구현 경로·현재 권한/회수·쿠키/CSRF 규격을 인계해야 합니다. 임시 인증을 운영 인증으로 대신 연결하지 않습니다.
