## 2026-10-15 광고 로그 MongoDB 독립 관리

최신 사용자 결정으로 광고 관리·측정·소진 로그는 광고 MongoDB에 저장합니다. PostgreSQL 전달과 공통 로그 테이블 규격은 사용하지 않습니다. 새 `log_record`와 기존 기록 보존·점검/스키마 적용은 [광고 로그 저장 계약](../development/ads/MongoDB_광고_로그_저장_계약.md)을 따릅니다. 관리3+공개5+정책2 구조와 공유 ADMIN/guest 인증 경계는 유지합니다.

## 로컬 임시 관리 도구

최신 사용자 요청으로 [임시 광고 제어 도구](../development/ads/임시_광고_관리_도구.md)를 별도 추가합니다. 저장소 루트에서 `ad-server/backend/.venv/Scripts/python.exe ad-server/backend/sandbox.py --start-mongo`로 실행하는 진입점이며 `--start-mongo`는 로컬 `.tools/mongodb-test/mongod.exe` 사용 시의 선택 기능입니다. Edge/Chrome에서 `http://127.0.0.1:8001/dev/ads/`를 직접 열고 Git 제외 `.local/ads-sandbox/access.txt`의 실행별 코드를 입력합니다. 2026-10-16 no-referrer/Origin 충돌을 수정했고 내장 브라우저 로그인·미리보기·수동 갱신을 확인했습니다. CSRF/출처 검사는 유지하며 도구 안내의 최신 정정을 따릅니다. 기존 `.env`를 읽지 않는 sandbox 설정/URLconf와 별도 `ads_sandbox_dev/is_test=true`를 사용합니다.

기존 광고 관리 API·5분 반복 검증/명시 수동 갱신을 확인하고 새 광고 로그는 MongoDB log_record에 저장하고 이전 기록은 보존합니다. is_test=true 측정은 MEASUREMENT_UNAVAILABLE·운영 카운트/예상량0이며 운영 flag 우회/가짜 원장 주입으로 소진시키지 않습니다. 이 도구의 개발 인증/guest는 공유 PostgreSQL 연결이 아니며 정식 React 관리자나 공통 ADMIN/공개/운영 통합의 완료로 처리하지 않습니다. 직접 시작한 DB 프로세스만 Ctrl+C 종료와 함께 정리합니다. 현재 구현/실제 실행 여부·검증 결과는 도구 안내와 광고 수용 기록을 함께 확인합니다.

## 2. Python 서버 기반

기본 절차는 [backend README](../../ad-server/backend/README.md)입니다. 로컬에서는 Python 3.12.13과
잠금된 패키지를 설치했습니다. 이 워크스페이스의 Python 런타임은 `.tools/python/`,
가상환경은 `ad-server/backend/.venv/`, 설치 캐시는 `.cache/uv/`에 두며 모두 추적하지 않습니다.

```powershell
Set-Location -LiteralPath 'C:\MLO01-01\Chapter3,4 mission\ad-server\backend'
$env:PYTHONIOENCODING='utf-8'
.\.venv\Scripts\python.exe manage.py check
.\.venv\Scripts\python.exe manage.py test tests --verbosity 2
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe manage.py run_ads_dev
```

`run_ads_dev`는 공통 DB migration 확인 없이 광고 경로를 실행하는 DEBUG 개발 서버입니다.
loopback `127.0.0.1:8000`으로 실행하며 Ctrl+C로 종료합니다. health의 200은 DB 연결·ADMIN 인증·
광고 관리/측정 완료를 뜻하지 않습니다. 관리자 요청은 공유 인증 어댑터 미연결 시 503입니다.
실제 공통 PostgreSQL이 연결되면 일반 Django 개발 서버와
운영 WSGI·Gunicorn/systemd 실행안을 INF와 연결합니다.

서버 실행 설정: `DJANGO_DEBUG`, `DJANGO_SECRET_KEY`, `DJANGO_ALLOWED_HOSTS`.
공통 DB 설정: `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_HOST`, `POSTGRES_PORT`.
광고 DB 설정: `ADS_MONGODB_URI`, `ADS_MONGODB_DATABASE`.
실제 값은 추적하지 않는 `ad-server/backend/.env`에서 관리합니다.

공통 ADMIN/세션 검증은 `ADS_ADMIN_AUTHORIZER`의 서버 callable로 연결합니다. 매 요청 현재 활성/
ADMIN·광고 권한을 검사하는 반환 DTO는 `api.ads_auth.AdminIdentity`입니다. 실제 공유 세션 검증 방식과
권한 매핑은 공통 담당자가 구현합니다. 미설정/장애는 503, 미로그인/비활성 401, 무권한 403입니다.
Origin/CSRF는 JSON 본문 해석 전에 원본 Django request에서 검사합니다. 클라이언트 역할/ID를 믿거나
광고 DB에 계정/세션을 만들지 않습니다. 테스트 인증 fixture는 테스트 파일에만 있습니다.

광고 관리·측정·소진 로그는 MongoDB의 log_record에 업무와 원자 저장합니다. 외부 로그 전달은 사용하지 않으며 check_ads_logs로 조회/표본 무결성을 점검합니다.

공개 API에는 다음 네 설정이 추가로 필요합니다. 실제 값이나 임의 운영 정책은 이 문서에서 만들지 않습니다.

| 설정 | 연결할 내용 |
|---|---|
| `ADS_GUEST_CONTEXT_PROVIDER` | 공유 guest를 검증/발급하는 서버 callable; `PublicGuestContext` 반환 |
| `ADS_PUBLIC_POLICY_PROVIDER` | `domains.ads.runtime_policy.get_public_policy` 명시 연결; 확정1800초·분리 마감·예산 이력 검사 |
| `ADS_DELIVERY_SIGNING_KEY` | 서버 배달 HMAC 서명키; `.env`에서만 관리 |
| `ADS_PUBLIC_BASE_URL` | 실제 절대 HTTPS 공개 주소 |

guest 미연결은 `GUEST_UNAVAILABLE`/503, 정책/서명/주소 미설정·실패는 `ADS_POLICY_UNAVAILABLE`/503입니다.
이미지 읽기는 guest provider를 호출하지 않고 배달 proof와 정책을 확인합니다. callback은 MongoDB
트랜잭션 안에서 재실행될 수 있으므로 외부 API·PostgreSQL·파일·네트워크 I/O를 실행하지 않습니다.
guest 확인은 업무 트랜잭션 밖이며 광고 로그는 MongoDB에 함께 저장합니다.

[정책 결정 가이드](../development/ads/광고_미정_정책_결정_가이드.md#2026-10-15-사용자-답변-반영)의 현재 결정은 배달30분·표시/보고 분리·소재 교체 처리·통계/예산 모두5분·수동 중단 유지입니다. `.env.example`의 정책 경로는 선택 설정이며 실제 `.env`·공유 guest·서명키·HTTPS 주소를 연결해야 합니다. runtime provider는1800초·split_deadlines=True·check_budget_history=True·cap_at_midnight=False입니다. fixture900초/허용 callback을 운영 기본값으로 사용하지 않습니다.

신규 배달은 display_expires_at과300초 뒤 event_expires_at을 나누고 budget_policy_version을 서명에 포함합니다. 기존 필드/marker 없는 배달은 수명·서명을 늘리거나 예산 이력 정책을 소급하지 않습니다. 자정 배달 단축은 기본 False이며 KST 발생일 기준을 별도 경계값 승인으로 표현하지 않습니다.

5분 원장 검증에서 소진 확인 최초 cutoff를 고정하고 이후 새 배달/재확인/이미지를 막습니다. occurred_at < cutoff인 유효 보고는300초 이내 초과 인정, 경계 이상은 제외합니다. 잔여23/20 최소 조건·예약은 없습니다. 자동 종료는 소진/게시 기간 끝이며 paused는 별도 유지합니다. 예산 쌍은 관리API 입력이고 실금액 기본값은 없습니다. 미설정/상태누락 광고는 부적격, 상태가300초 초과 오래됐거나 future/잘못된 형식이면503 기술 장애입니다.

배치/relay 코드를 구현했지만 실제 watch·공유 인증·AWS·브라우저 실행은 미완료입니다. 제목/priority 상세와 미사용asset7일 정리도 승인된 실행 대상이 아닙니다.

## 3. 광고 MongoDB와 스키마

[로컬 MongoDB 안내](../../ad-server/config/environments/ads/README.md)에 따라 Linux Docker 엔진을 준비합니다.
단일 멤버 replica set `ads-rs`는 로컬 트랜잭션 개발용이며 HA를 제공하지 않습니다.
포트는 loopback에만 공개합니다. 실제 DB/콘테이너 기동 여부는 검증 문서에서 구분합니다.

```powershell
# 저장소 루트에서 실행
docker compose -f ad-server/config/environments/ads/docker-compose.yml config --quiet
docker compose -f ad-server/config/environments/ads/docker-compose.yml up -d
docker compose -f ad-server/config/environments/ads/docker-compose.yml wait mongo-init
docker compose -f ad-server/config/environments/ads/docker-compose.yml up -d --wait --wait-timeout 120 mongo
```

초기화 성공과 primary를 확인한 뒤 backend에서 실행합니다.

```powershell
# 정의만 표시; DB를 변경하지 않음
.\.venv\Scripts\python.exe manage.py apply_ads_schema
.\.venv\Scripts\python.exe manage.py apply_ads_public_schema
.\.venv\Scripts\python.exe manage.py apply_ads_policy_schema
# 로컬 advertising_dev DB에 세 컬렉션·validator·인덱스 적용
.\.venv\Scripts\python.exe manage.py apply_ads_schema --apply
# 공개 상태의 추가 다섯 컬렉션·validator·인덱스 적용
.\.venv\Scripts\python.exe manage.py apply_ads_public_schema --apply
# 정책 2컬렉션·validator·인덱스 적용
.\.venv\Scripts\python.exe manage.py apply_ads_policy_schema --apply
# replica set primary와 트랜잭션 읽기 확인
.\.venv\Scripts\python.exe manage.py check_ads_database
# MongoDB 광고 로그 읽기 점검
# 원장 기준 예산 검증·통계 재계산 1회
.\.venv\Scripts\python.exe manage.py refresh_ads_policy
# 상시 실행이 필요할 때 별도 프로세스로 시작; 300초 시작 간격, Ctrl+C 종료
.\.venv\Scripts\python.exe manage.py refresh_ads_policy --watch
```

개발 명령은 loopback URI와 `_dev` DB명만 허용합니다. URI를 출력하지 않습니다.
DDL 적용은 컬렉션별 순차 작업이며 전체 DDL 하나의 트랜잭션은 아닙니다. 중간 실패면 원인을
확인한 뒤 같은 manifest를 재적용합니다. 기존 자료의 소급 검증·데이터 삭제·운영 migration은 하지 않습니다.

관리 세 컬렉션은 [관리 데이터 정의](../../ad-server/backend/domains/ads/schemas/management_manifest.json),
공개 다섯 컬렉션은 [공개 상태 정의](../../ad-server/backend/domains/ads/schemas/public_manifest.json)를 따릅니다.
공개 상태는 `ad_rotation_state`, `ad_deliveries`, `ad_events`, `ad_repeat_windows`,
`ad_estimated_usage_ledger`입니다. claim은 배달 내부, 측정 log_record는 event 내부에 있습니다.
정책 [정의](../../ad-server/backend/domains/ads/schemas/policy_manifest.json)는 `ad_budget_states`, `ad_daily_metrics` 두 개입니다. 합계10개이며 세 manifest는 별도 순차 적용합니다. 별도 claim·사용자·outbox·ad_versions 컬렉션을 만들지 않습니다.
측정 원본은 received_at부터 90일, 예상 원장은 processed_at부터 365일인 기존 보관 기준을 유지합니다.
감사/멱등·PENDING 보호와 배달/이미지 공유 참조를 확인하는 정리 작업은 미구현이므로 삭제 예정 시각을
계산하지 않고 `retention_due_at=null`로 둡니다. 자동 TTL도 설정하지 않습니다.

## 4. 인프라 담당자와 맞출 부분

현재 origin/feature/infra를 읽기 전용으로 확인한 결과입니다. 설치·운영 상태를 뜻하지 않습니다.

- 인프라 인계의 일부 FastAPI 표현은 최신 main의 Django/DRF 계약과 다릅니다.
- 인프라 MongoDB 설치 코드는 standalone이어서 광고 업무 트랜잭션용 replica set 보완이 필요합니다.
- 광고 EC2의 별도 포트/라우팅·공통 ADMIN 검증·MongoDB 권한/복구 경로가 미확정입니다.
- MongoDB 광고 DB명/authSource는 인프라의 advertising 예시와 로컬 advertising_dev를 구분합니다.
- AWS 인증·TLS·최소 권한·백업·복구는 이 로컬 Compose를 그대로 배포해 완료 처리하지 않습니다.

인프라 설치 스크립트는 워크스테이션에서 실행하지 않았고, 공유 DB나 AWS 자원은 변경하지 않았습니다.
수업의 구체 교안·실습 코드는 미수령입니다. 추가 자료가 오면 광고 저장/API/선정/측정/토큰 흐름과
현재 계약의 차이를 확인해 적용합니다.

## 5. 공개 API·측정 원자 저장과 검증

후속 [광고 남은 작업·연결 계획](../development/ads/광고_남은_작업과_연결_계획.md)에
`run_ads_workers`(단발/명시 독립 반복)와 `check_ads_runtime`(읽기 점검)의 사용법을 정리했습니다.
광고 로그는 MongoDB에 원자 저장하고 정책 실패 재시도·스키마/로그 점검을 제공하며,
공유 인증·운영 배치 설치·보관/복구·화면 통합은 별도 인계로 유지합니다.

[공개 선정·측정 로직 인계](../development/ads/공개_선정과_측정_로직_인계.md)의
selection.py/measurement.py는 DB·HTTP를 실행하지 않는 규칙 모듈입니다.
public_service.py·ads_public_mongo.py·api/ads_public.py가 업무/저장/HTTP를 연결합니다.

| 경로 | 사용 방식 |
|---|---|
| `GET /api/ads` | 필수 placement; 신규 발급 또는 delivery_id와 `X-Ad-Delivery-Token` 재확인; 신규 멱등 재전송에 `Idempotency-Key` |
| `POST /api/ad-events` | event_id·delivery_id·event_type·occurred_at JSON과 `X-Ad-Delivery-Token`; Origin/CSRF 먼저 검사 |
| `GET /api/ad-deliveries/{delivery_id}/image` | delivery_token query proof·현재 게시 자격 확인 후 이미지 |

광고 관리·측정·소진 로그는 MongoDB의 log_record에 업무와 원자 저장합니다. 외부 로그 전달은 사용하지 않으며 check_ads_logs로 조회/표본 무결성을 점검합니다.

ad-server/backend에서 다음 검증 명령을 사용합니다. 실제 실행 결과는 검증 기록을 따릅니다.

```powershell
$env:PYTHONUTF8='1'
$env:PYTHONIOENCODING='utf-8'
.\.venv\Scripts\python.exe manage.py test tests --verbosity 1
.\.venv\Scripts\python.exe -m ruff check .
```

실제 replica set 검증은 localhost `ads-rs`가 준비된 경우에만 `ADS_RUN_MONGO_TESTS=1`과
`ADS_TEST_MONGODB_URI`를 지정해 `tests.test_ads_public_mongo_integration`을 선택 실행합니다.
시험은 무작위 UUID `_dev` DB만 만들고 정리하며 공유/운영 DB는 사용하지 않습니다.

5분 통계는 원장 범위를 재계산해 교체합니다. summary는 오늘, 목록 행 measurement는 보존 범위 누적이며 as_of·aggregation_status·coverage·coverage_from/coverage_through·is_stale를 표시합니다. 연결 전 null/PENDING과 실제0을 구분합니다. 브라우저의 실제 노출 조건과
중단 후 3초 이내 숨김, 공유 환경·정책·운영 인프라·복구 연결은 별도입니다. 태그/업종 매칭은 4차로 유지합니다.
