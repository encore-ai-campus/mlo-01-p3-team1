취소 요청 본문은 `{}`이며 `Idempotency-Key`가 필요합니다. 응답은 `{job_id,status,playlist_id}`입니다. 타인/없는 작업은 동일한 404, 잘못된 본문/키는 422, CSRF 오류는 403입니다. 기존 GET 작업 상세는 `CANCELLED`도 그대로 반환합니다.

작업자 `worker.run_one`은 이미 결과 저장 시 같은 Job 행을 잠그고 RUNNING·lease 토큰·세대·만료를 검사합니다. 취소가 먼저 확정되면 결과·PLAYLIST_GENERATED 이벤트를 저장할 수 없고 재claim/heartbeat도 중단됩니다. 완료 저장이 먼저 확정되면 SUCCEEDED와 기존 결과 ID를 반환하여 완료된 결과를 삭제하지 않습니다. 실패/만료 작업도 상태를 보존합니다. 부모 결과·제외 revision·승인 revision은 취소로 변경하지 않습니다.

진행 중인 계산 스레드나 이미 외부에 발송된 Gemini HTTP 요청을 강제 종료하는 기능은 아닙니다. 계산/외부 호출은 기존 제한 시간까지 이어질 수 있으나 취소 후 결과 커밋은 차단됩니다. 이미 발송한 외부 호출의 과금 취소를 보장하지 않습니다. 유료 모델 호출은 이번 검증에서 실행하지 않았습니다.

기존 운영 수집기의 추천 terminal 집계는 SUCCEEDED/FAILED/EXPIRED만 대상으로 하므로 CANCELLED는 성공률 분모에 포함되지 않습니다. 취소율 전용 지표는 이번 범위에서 추가하지 않았습니다.

## 100% 배율·하단 광고 분석 (구현하지 않음)

100% 배율은 해상도가 아니라 브라우저 확대 비율입니다. 실제 배치는 OS 배율과 브라우저 도구 모음을 제외한 CSS viewport 크기를 기준으로 판단해야 합니다. 운영 원본 화면을 실제 브라우저에서 측정했습니다. 기존 선택 지역을 유지한 상태이며 지역명 확대 등 수정본 측정과 구분합니다.

| CSS viewport | 하단 광고 시작 | 광고 높이 | 광고 끝까지 필요한 높이 | 판단 |
|---|---:|---:|---:|---|
| 1920×1080 | 약 948px | 104px | 약 1052px | 화면 안에 표시 가능 |
| 1440×900 | 약 948px | 104px | 약 1052px | 약 152px 추가 스크롤 필요 |
| 1366×768 | 약 948px | 104px | 약 1052px | 약 284px 추가 스크롤 필요 |

주요 구성은 header 62px, 상단 광고 120px, 날씨 패널 약 148px, 카드 574px, 하단 광고 104px 및 여백입니다. 1280×720 실측에서는 전체 콘텐츠 약 1050px로 하단 광고가 첫 화면 밖입니다. 1920×1080 모니터라도 브라우저 내용 높이가 1080px보다 작으면 광고가 일부 가려질 수 있습니다.

전체 축소로 768px에 끼워 맞추면 약 27%를 줄여야 하므로 작은 글씨·평가/제외 버튼·팝오버·목록 조작이 더 어려워집니다. 글씨/버튼보다 이미지·카드 고정 높이·여백을 먼저 조절하는 편이 적합합니다. 1100px 이하에는 기존 2열, 700px 이하에는 1열로 쌓이므로 모든 요소와 하단 광고를 한 화면에 강제하는 목표는 부적절합니다.

일반 콘텐츠 페이지는 문서 흐름에 따라 세로 스크롤과 하단 광고를 허용하고, 업무/음악 앱은 화면 높이에 맞는 본문 프레임·목록 내부 스크롤·항상 찾기 쉬운 주요 작업 영역을 사용합니다. 이 서비스에는 큰 화면 3열 유지, 짧은 화면에서 앨범 이미지와 부가 안내·여백 우선 축소, 조건 선택/추천/취소/목록의 최소 조작 크기 유지, 작은 화면 자연스러운 문서 스크롤을 권합니다. 하단 광고 상시 노출이 사업상 필수라면 화면 높이 예산과 더 작은 전용 광고 소재를 별도 합의해야 합니다. 광고를 fixed overlay로 올려 음악 버튼을 덮거나 페이지 전체 zoom/scale을 낮추는 방안은 권하지 않습니다.

현재 Banner는 화면 50% 이상·1초 이상·이미지 로드 완료·활성 탭 조건에서 노출을 기록합니다. 하단 광고를 요청했다는 사실만으로 노출로 세지 않으며, 배치 변경 시 이 기준과 클릭/목록 가림 여부를 함께 검증해야 합니다.

근거: [W3C Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html), [web.dev 반응형 설계](https://web.dev/articles/responsive-web-design-basics). 모든 내용을 한 화면에 넣는 요구보다 확대/좁은 창에서도 정보와 기능을 유지하고 읽기 방향의 스크롤을 허용하는 접근을 참고했습니다. 위 배치 방향은 제안이며 이번에 적용한 변경이 아닙니다.
