운영 provider는 `domains.ads.runtime_policy.get_public_policy`이며1800초·split_deadlines=True·check_budget_history=True·cap_at_midnight=False입니다. .env.example에는 선택 경로를 적었지만 실제 환경 비밀 설정/공유 guest·HTTPS·서명키·sink를 연결해야 합니다. 상태 누락은 부적격,300초 초과 stale는503 기술 장애이며 새 캠페인 종료 조건이 아닙니다. 실제 watch·공유PostgreSQL·AWS·브라우저 실행은 완료하지 않았습니다.

테스트의900초를 운영값으로 승격하지 않습니다. 제목100자/priority100/asset7일은 이 선택에 포함하지 않았습니다. 아래 보존 초안의 자정 표시 종료·최소23/20·기발급 유지·매요청 예산 판정은 현재 정책이 아닙니다.

## 2. 배달 수명 — 표시와 보고를 나누기

delivery는 특정 광고·소재·위치를 한 번 제공한 단위입니다. 사용자 로그인 토큰이나 과금 잔액이 아닙니다.
아래 네 시간을 구분해야 만료 직전 발생한 정상 보고가 빠지지 않습니다.

| 시간 | 의미 | 제안/확정 구분 |
|---|---|---|
| 표시 유효기한 | 지금 받은 배너 응답을 언제까지 표시할 수 있는가 | 평가 후 최대3초, 재확인1초는 확정 |
| 배달의 표시 수명 | 같은 delivery를 언제까지 유지할 것인가 | **30분을 논의 시작값으로 제안** |
| 보고 기한 | 표시 수명 안에서 발생한 이벤트가 언제까지 도착할 수 있는가 | 표시 만료 뒤에도 지연300초 이내 검사하도록 분리 제안 |
| 자료 보관 기간 | 만료한 delivery/이벤트의 근거를 얼마나 보존하는가 | 기존90일 기준 유지, 삭제는 참조/pending 보호 필요 |

30분을 제안하는 이유는 오래 사용하는 카페 화면에서 만료에 따른 교체를 위치당 시간당2회 수준으로 제한하기 위해서입니다.
짧은 수명은 광고 교체와 새 노출 인정 기회를 늘리고, 긴 수명은 같은 배너를 오래 유지합니다.
이는 논의용 선택이며, 5분이나15분으로 바꾸려면 이 차이를 함께 선택하면 됩니다.

**추천 동작 초안**은 다음과 같습니다.

1. 신규 진입 시 delivery를 발급하고,1초 재확인은 같은 delivery를 유지합니다.
2. 표시 마감은 발급 후30분·광고 종료·다음 KST 자정 중 가장 이른 시각으로 잡습니다.
3. 만료·소재/위치 변경 시 옛 배너와 노출 타이머를 종료하고, 새 발급 요청을 한 번 시작합니다.
4. 신규 발급에는 새 멱등키를 쓰고, 응답 유실 재시도에는 같은 키를 씁니다. 기존 키 재사용은 최초 응답 재반환입니다.
5. 새 배달도 기존 반복 제한을 적용합니다. 재확인·발급 자체는 유효 노출이 아닙니다.
6. 통신 실패로 숨긴 뒤 복구할 때는 아직 유효한 같은 배달부터 재확인합니다. 탭 복귀 자체로 새 배달을 만들지 않습니다.

30분마다 재발급을 선택하면, 같은 페이지를 계속 보는 이용자도 새 배달에서 조건을 충족할 때 추가 예상 노출량이 생길 수 있습니다.
이 동작을 원하지 않으면 자동 재발급 대신 페이지 재진입/명시 교체 때만 발급하는 대안을 선택해야 합니다.
정상 광고 없음에는 연속 즉시 발급을 반복하지 않고, 공개 화면 담당자와 재조회 간격을 따로 맞춥니다.

예를 들어23:50에 발급한 배달은 자정에서 표시가 끝납니다.23:59:59에 발생하고00:04:59에 도착한 보고는
지연300초 경계의 전날 이벤트로 검사합니다. 자정에 옛 배달로 발생한 새 이벤트는 제외하고 새 배달을 사용합니다.
소재 수정·관리자 중단이 더 이르면 그 효력 시각부터 옛 배달의 새 표시/발생은 차단합니다.

**필요한 코드 변경:** 현재는 `event_expires_at` 하나를 표시와 수신 마감에 함께 사용합니다.
이 초안을 채택하면 표시 마감과 보고 마감을 분리하고, 발생 시각은 표시 유효 구간 안인지 검사해야 합니다.
예상 필드명 `display_expires_at`/`report_expires_at`은 설계 후보이며 아직 실제 필드가 아닙니다.
수신 지연은 정확히300초까지 허용하되, 만료 후 새 발생을 보고 유예로 인정하지 않습니다.

## 3. 소재 수정 — 옛 배달을 덮어쓰지 않기

제목·이미지·링크를 바꾸면 옛 배달의 앞으로의 표시는 막고 새 소재를 발급하는 방향을 권합니다.
수정 전에 발생한 정상 이벤트와 이미 저장한 최초 판정은 유지합니다.

| 변경 | 추천 처리 초안 |
|---|---|
| 제목·이미지·링크 | 새 creative_version, 옛 배달의 새 표시/변경 이후 발생 차단, 변경 전 발생은300초 지연 검사 |
| placement | 옛 위치 배달 차단, 새 위치에서 신규 발급; 다른 위치 배너에 옛 배달을 이동시키지 않음 |
| 시작/종료 일정 | 과거 판정은 유지하고 현재 일정 검사. 종료 단축은 즉시 표시 기한에 반영, 연장만으로 옛 배달 수명을 늘리지 않음 |
| priority | 다음 신규 선정부터 적용. 기존 유효 배달은 유지 |
| 중단 | 신규 발급/새 발생 차단, 기존3초 화면 반영 유지, 중단 전 발생은300초 지연 검사 |
| 예산 변경 | 과거 원장 유지, 신규 제공 판정에 새 값 적용. 예산 부족과 관리자의 paused 상태는 분리 |

현재 creative_version은 제목·asset_id·link_url 변경에만 갱신됩니다. 위치·일정·priority는 별도로 검사해야 합니다.
같은 광고의 소재를 바꿔도 노출60초/클릭300초 반복 창은 초기화하지 않습니다.
이미 발급한 proof와 감사 이력을 삭제해 과거 유효 보고나 같은 event_id의 최초 응답 재반환을 막는 방식은 피합니다.

## 4. 예산 — 먼저 초과 허용 여부 선택하기

광고별 일일 예산과 전체 예산을 두는 방향은 기존 계약에 있습니다. 실제 금액과 초과 처리 방식이 미정입니다.
예산 토큰은 예상 사용량 단위이며, 원화 환산·구매·환불은 여기서 정하지 않습니다.

| 선택 | A. 원장 기준 신규 제공 중단 | B. 최대 예상량 예약 |
|---|---|---|
| 처리 | 새 발급 시 이미 확정된 예상 원장 합계로 예산 판정 | 발급 전에 배달의 최대 예상량을 확보하고 인정 시 소비로 전환 |
| 구조 | 기존 원장 활용, 예약 상태 추가 없음 | 예약량·소비/해제·만료 회수·복구 상태 필요 |
| 소진 후 기발급 배달 | 원래 유효 구간까지 유지하고 정상 보고는 기록 | 확보한 예약 범위 안에서 처리 |
| 초과 | 미보고 배달/동시 요청 때문에 발생 가능 | 예약·일일 경계·복구까지 원자 제어하면 초과0을 목표로 검증 가능 |
| 적합한 방향 | 실제 차감 없는 초기 시연, 초과 가능성을 명시해 수용 | 상한이 반드시 지켜져야 하는 운영 |

현재 프로젝트에는 **초과 가능성을 받아들이는 경우 A안을 우선 권합니다.** 실시간 대시보드나 별도 예약 체계를 만들지 않고
기존 원장을 활용할 수 있습니다. 초과0이 요구되면 처음부터 B안을 선택해야 합니다.
통계를5분마다 보여주는 것과, 발급 경로에서 예산을 검사하는 것은 별개의 작업입니다.

### A안을 고를 때 함께 정할 규칙

- 발급 시 일일/전체 잔여량 모두 해당 위치의 최대액 이상이어야 새 배달을 제공합니다. 상단23·하단20토큰입니다.
- 소진 확인 뒤 신규 발급은 막고, 이미 발급한 유효 배달은 유지합니다. 남은 금액이 최대액보다 작으면 사용하지 못할 수 있습니다.
- 예산을 넘겨 도착한 기발급 정상 보고도 예상 원장에는 그대로 남기고 초과량을 구분합니다. 단가를 깎거나 과거 판정을 지우지 않습니다.
- 이 방식의 초과량에는 전역 고정 상한이 없습니다. “최대23토큰 초과”처럼 한 배달의 한도를 전체 보장으로 쓰지 않습니다.

예: 일일 한도1,000·현재970토큰인 상단 광고에서 서로 다른 guest에게4개 배달이 보고 전에 발급되면, 각 요청은 남은30토큰을 보고 통과할 수 있습니다.
네 배달이 각각 노출+클릭23을 인정받으면 합계는1,062토큰입니다. 광고 문서 잠금만으로 미보고 비용이 예약되지는 않습니다.
이 숫자는 설명용 예시이며 운영 예산값이 아닙니다.

“최대5%까지만 초과” 같은 조건을 원하면 A안만으로 보장할 수 없습니다.
미처리 배달 수/위험액 제한이나 예약 제어를 추가로 설계해야 합니다.

### B안을 고를 때 추가되는 규칙

상단 배달은 최대23·하단은20토큰을 일일/전체 예산 양쪽에 예약합니다. 정상 인정분은 소비로 전환하고,
억제된 유형의 예약은 해제합니다. 아직 보고되지 않은 유형은 보고 기한과 기한 내 수신된 미처리 작업을 확인한 뒤 해제합니다.
클릭만 먼저 인정되면15를 소비하고 노출 가능분은 남겨 둡니다. 예약 자체는 노출/클릭 실적이나 실제 차감이 아닙니다.
발급·예약, 이벤트·소비/해제, 만료 회수를 각각 원자 처리하고 재시작/중복 실행도 검증해야 합니다.
현재 budget callback만 교체해서 완료할 수 있는 범위는 아닙니다.

### 공통으로 추천하는 경계

| 항목 | 추천 초안 |
|---|---|
| 일일 경계 | KST00:00~다음00:00, 사용량은 검증된 발생일에 귀속 |
| 일일 전환 | 날짜별 원장 조회로 구분. 자정에 과거 사용량을 지우거나 원장을 초기화하지 않음 |
| 자정에 걸친 배달 | 자정에 표시 만료·새날 새 배달. 전날 보고 유예는 전날 원장/예약에 귀속 |
| 예산 입력 | 일일/전체 모두 양의 정수, 미설정 광고는 공개 제공 부적격. 실제 숫자는 광고별 결정 |
| 예산 하향 | A안은 과거 원장을 줄이지 않고 새 한도 기준으로 추가 발급 차단. B안은 소비+예약보다 낮은 변경을 거절하는 방향 |
| 증액/다음날 | 관리 중단이 아니고 기간/소재/예산이 적격이면 신규 제공 가능. paused는 자동 해제하지 않음 |

관리자가 오늘 요약에서 보는 합계는 지연될 수 있으므로 발급 예산 판정에 그 배치 합계를 그대로 쓰지 않습니다.
365일 원장만으로 영구 누적 예산을 계산할 수는 없습니다. 장기 광고는 보관 범위와 전체 예산 누적 근거를 별도 설계해야 합니다.
현재 코드는 기존 배달 재확인/이미지에도 budget_eligible을 호출하므로, A안의 ‘신규만 차단’은 호출 경계를 분리해야 합니다.

## 5. 통계와 부수 정책 — 필요한 만큼만 정하기

통계는 **5분 주기 집계를 시작안으로 제안**합니다. 오늘 노출·클릭·예상 토큰, 광고별 누적을 기존 화면 담당자에게 제공합니다.
연결 전 null/PENDING과 연결된 실제0을 구분하고, 집계 기준시각·조회 가능 범위·지연 상태를 함께 반환합니다.
배치는 원장/최초 판정의 대상 범위를 재계산해 교체하여 재실행 중복을 막는 방향을 권합니다.

자정 뒤 전날 이벤트가 도착하므로 오늘/전날을 보완 집계합니다. 처리 적체로 더 늦게 커밋된 자료도 변경 날짜를 다시 집계합니다.
00:05를 전날 통계의 무조건 확정 시각으로 약속하지 않습니다.90일 원본이 사라진 뒤에는365일 원장/보존 집계를 활용하고
원본 상세를 다시 검증할 수 있는 것처럼 표시하지 않습니다.

| 나머지 항목 | 다음 합의에 제시할 시작안 — 아직 미채택 |
|---|---|
| 재개 | 첫 운영에서는 재개 기능 보류, 관리 중단을 일반 PUT으로 해제하지 않음. 재개가 필요하면 명시 API/권한부터 설계 |
| 입력 제한 | 제목1~100자, priority0~100 정수 제안. 높은 값 우선은 유지하고 문자열 길이 기준은 API에서 통일 |
| 미사용 이미지 | 업로드7일 후 정리 후보 제안. 현재 광고·보관할 배달/감사·pending 참조가 하나라도 있으면 보호, 우선 dry-run 목록으로 검수 |
| 파일 캐시 | 현재 delivery별 proof 조회와 no-store 유지 제안. 공개 HTTPS 주소와 proxy는 INF/C와 실제 연결 |
| 관리 권한 | 현재 read/write 분리를 공유 ADMIN의 실제 권한에 매핑. 공통 사용자 DB/쿠키를 광고에서 새로 만들지 않음 |

이 표의 부수 정책은 관리 통계 5분과 별도입니다. 제목1~100자·priority0~100·미사용 이미지7일 등
상세값의 승인 여부는 아직 불명확하므로 이번 코드 변경에 포함하지 않고 남은 결정으로 둡니다.

재개·이미지 실제 삭제·365일 초과 누적/백업 보관은 핵심 공개 정책과 분리해 후속으로 결정할 수 있습니다.
