# 광고 데이터와 로직 설계 — 개발 준비안

- 작성일: 2026-10-15
- 수정일: 2026-10-15
- 범위: 3차 카페 광고의 서버 로직·MongoDB 데이터 구조·관리 화면 연결 계약
- 개발 브랜치: `feature/ad-logic` — 단일 광고 개발 브랜치
- 사용자 역할 정정: 관리자 페이지는 다른 담당자가 제작합니다. 이 작업은 광고 관련 로직 설계와 백엔드 개발 준비를 담당합니다.
- 상태: 관리·공개 API와 원자 저장·5분 예산/통계·관리/측정/소진 relay 코드를 연결했습니다. 공유 인증/guest·로그 sink·상시 watch·공개 배너/AWS 운영 완료는 별도입니다.
- 수업 반영: 사용자가 알려 주신 수업 주제는 광고 서버 구축입니다. 실제 교안·실습 코드는 받지 않았으며, 광고 저장 → 관리 API → 공개 제공 → 측정 → 토큰 집계의 흐름을 이해하고 구현할 수 있도록 구성했습니다.

이 문서는 광고 서버가 저장하고 판정해야 할 내용을 정리합니다. 관리자 화면 담당자는 아래 API 계약을 사용하여 음악·피드백·광고 메뉴를 하나의 화면에서 연결할 수 있습니다. 광고 데이터 모델에 음악·피드백의 테이블을 합치지 않습니다.

## 1. 적용 기준과 첫 개발 범위

[ADS 안내](../../handoff/ads/README.md)의 읽는 순서와 [최신 통합 인계](../../handoff/ads/05_광고_간소화_통합과_추가_인계.md)를 적용합니다. [간소화 원문](../../handoff/ads/04_광고_관리_간소화_인수인계서.md)은 필드·멱등·감사 구조를 참고하되, 원문의 업종 태그 부분은 4차 참고입니다.

| 단계 | 광고 서버가 준비할 결과 | 저장 범위 |
|---|---|---|
| 첫 관리 | 이미지 검사·저장, 광고 등록/수정/중단·목록·서버 상태, 감사·멱등·로그 전달 | `ads`, `ad_assets`, `ad_admin_changes` |
| 공개·측정 구현 | 위치별 광고 선정·순환·delivery, 중단 반영, 노출/클릭 최초 판정·중복 방지·예상 항목 저장 | `ad_rotation_state`, `ad_deliveries`, `ad_events`, `ad_repeat_windows`, `ad_estimated_usage_ledger` |
| 5분 통계·예산 구현 | 원장 합계 검증·소진 cutoff·신규/열린 배달 차단·관리 통계 재계산 | `ad_budget_states`, `ad_daily_metrics` |

3차에는 광고 대상이 카페로 고정됩니다. `targeting_mode`, `target_tag_codes`, `tag_catalog_version`, `targeting_policy_version`과 사용자 업종 입력을 요청·저장에 추가하지 않습니다. 알 수 없는 입력 필드는 무시하지 않고 거부합니다. 별도 태그 사전 API도 만들지 않습니다.

관리 화면 제작은 별도 담당자의 작업입니다. 기존 기획 문서의 B 담당 광고 관리 화면 배정은 사용자 정정과 다르며, 이 준비안의 작업 범위는 광고 서버로 한정합니다. 기존 태스크 ID·직접 선행 관계·팀 문서는 여기서 변경하지 않습니다.

## 2. 서버와 저장소의 연결

```mermaid
flowchart LR
    UI[다른 담당자의 통합 관리 화면] --> API[광고 API · Django/DRF]
    AUTH[공통 ADMIN 인증 · PostgreSQL] --> API
    PUBLIC[다른 담당자의 공개 배너] --> API
    GUEST[공통 guest 문맥] --> API
    API --> DOMAIN[입력·상태·version·멱등 판정]
    DOMAIN --> MONGO[광고 MongoDB · 관리3 + 공개5 + 정책2컬렉션]
    MONGO --> RELAY[내장 관리·측정·소진 로그 relay]
    MONGO --> BATCH[5분 원장 검증·통계 재계산]
    BATCH --> MONGO
    RELAY -.-> LOG[연결 대기 · 공통 PostgreSQL 로그 사본]
```

- 계정·활성 ADMIN·권한·세션·guest의 원본은 공통 환경에 있습니다. 광고 DB에는 서버가 검증한 `identity_source`·외부 계정 ID와 검증한 guest 내부 ID만 참조합니다.
- 사용자 컬렉션, 비밀번호/해시, 이메일·프로필, 쿠키·세션 원문 토큰을 광고 DB에 복제하지 않습니다. 외부 ID를 MongoDB ObjectId로 강제 변환하지 않습니다.
- MongoDB는 별도 어댑터로 연결합니다. Django ORM의 모델·migration을 광고 MongoDB 테이블 생성 도구로 사용하지 않습니다.
- 광고 변경과 감사/멱등 기록은 같은 MongoDB replica set 트랜잭션에 저장합니다. 공통 인증 조회와 PostgreSQL 로그 전달은 이 트랜잭션 밖입니다.
- 광고 전용 논리 DB·권한·정리 범위는 날씨 MongoDB와 구분합니다. AWS 프라이빗 서브넷의 실제 주소·포트·서비스 배치·인증 라우팅은 INF 인계가 필요합니다.

## 3. 첫 단계 컬렉션 ERD

MongoDB에서는 아래 관계를 서비스 코드가 검사합니다. 그림의 FK는 관계를 설명하는 논리 참조이며 DB 간 자동 외래키를 뜻하지 않습니다.

```mermaid
erDiagram
    SHARED_ADMIN ||--o{ ADS : manages
    SHARED_ADMIN ||--o{ AD_ASSETS : uploads
    SHARED_ADMIN ||--o{ AD_ADMIN_CHANGES : acts
    AD_ASSETS ||--o{ ADS : supplies
    ADS |o--o{ AD_ADMIN_CHANGES : records
    AD_ASSETS |o--o{ AD_ADMIN_CHANGES : references
    SHARED_ADMIN {
        string identity_source PK
        string account_id PK
    }
    ADS {
        string _id PK
        string asset_id FK
        string title
        string placement
        date starts_at
        date ends_at
        boolean paused
        long version
        string creative_version
        long daily_budget_tokens
        long total_budget_tokens
        string budget_version
    }
    AD_ASSETS {
        string _id PK
        binary image_bytes
        string mime_type
        long byte_size
        string sha256
    }
    AD_ADMIN_CHANGES {
        string _id PK
        string ad_id FK
        string asset_id FK
        string actor_account_id
        string operation
        boolean changed
        object response_snapshot
        object log_relay
    }
```

`SHARED_ADMIN`은 공유 환경 경계를 설명하기 위한 표시입니다. 광고 DB에 실제 컬렉션을 생성하지 않습니다. 광고 한 건의 위치는 `top` 또는 `bottom` 하나이며, 같은 이미지를 양쪽에 게시하면 두 광고가 하나의 asset을 참조합니다. 일정·중단·지표·예산은 광고별로 다릅니다. 예산 쌍은 선택 필드이며 아래 입력 계약을 적용합니다.

### 3.1. 공통 데이터 표준

| 항목 | 저장·입출력 규칙 |
|---|---|
| 업무 ID | 서버 생성 불투명 문자열을 MongoDB `_id`로 사용; API에서는 `ad_id`, `asset_id`, `log_id`로 대응 |
| 이름·문자 | UTF-8, `snake_case` |
| 시각 | 저장은 UTC BSON Date, API는 UTC ISO 8601 `Z`, 관리 입력·표시는 KST |
| 기간 | `starts_at < ends_at`, 시작 포함·종료 미포함 |
| 정수 | BSON int/long; API는 bool·숫자 문자열·소수의 강제 변환을 금지 |
| 공통 필드 | 관리 문서에는 `schema_version`, `is_test`, `created_at`; `ads`에는 `updated_at`. 공개 문서에는 기술 스키마/환경과 문서별 발급·수신·처리/갱신 시각 사용 |
| 환경 | `is_test`는 서버 설정으로 결정; 테스트 namespace/DB를 운영과 구분 |
| 버전 | 관리/공개 데이터 `schema_version`, 편집 `version`, 표시 `creative_version`, 단가 정책 버전, 연결 운영 정책 버전을 서로 구분 |

광고 데이터 버전은 수령 인계의 `phase3-ads-data-20261014.3`을 참고하고, 현행 3차 필드는 ADS05의 카페 전용 결정에 따라 태그를 제외합니다. 공통 API 계약 버전은 기존 문서/fixture와 이벤트 schema의 값이 달라 보류되어 있으므로 이 준비안에서 자동 통합하지 않습니다.

### 3.2. `ads` — 광고 현재 설정

| 필드 | 타입·필수 여부 | 규칙 |
|---|---|---|
| `_id` | string · 필수 | API의 `ad_id` |
| `title` | string · 필수 | 제목; 길이 제한은 PL 인계 후 고정 |
| `link_url` | string · 필수 | 호스트가 있는 절대 HTTPS URL |
| `asset_id` | string · 필수 | 검사·저장된 `ad_assets._id` 참조 |
| `creative_version` | string · 필수 | 표시 소재 버전; 수정 전 자료 재현에 사용 |
| `placement` | string · 필수 | `top` / `bottom` |
| `starts_at`, `ends_at` | Date · 필수 | UTC, 시작 < 종료 |
| `priority` | integer · 필수 | 큰 값 우선; 허용 범위는 PL 인계 필요 |
| `version` | integer · 필수 | 양수; 구현의 새 광고 시작값은 1 |
| `paused` | boolean · 필수 | 서버가 관리; 일반 수정으로 해제하지 않음 |
| `stopped_at` | Date 또는 null · 필수 | 잠금 이후 트랜잭션 내 중단 적용 시각; 성공 커밋으로 확정, 초기 null |
| `created_by_account_id`, `updated_by_account_id` | string · 필수 | 현재 요청에서 검증한 공유 관리자 ID |
| `identity_source` | string · 필수 | 공유 ID의 원본 환경 |
| `daily_budget_tokens`, `total_budget_tokens` | positive int64 또는 null · legacy 저장 선택 | 관리 입력은 선택 쌍·명시 null 거부; 미설정은 운영 부적격 |
| `budget_version` | string 또는 null · legacy 저장 선택 | 예산 두 값 실제 변경에만 새 UUID |
| `budget_blocked_at`, `budget_blocked_until` | Date 또는 null · 선택 | 현재 예산의 소진 효력 구간; DAILY는 다음KST자정까지, TOTAL은 종료 없음 |
| `budget_blocked_version`, `budget_blocked_scope` | string 또는 null · 선택 | 판정 예산 버전과 DAILY/TOTAL; 배치만 기술 갱신 |
| `schema_version`, `is_test`, `created_at`, `updated_at` | 공통 타입 · 필수 | 서버 설정·시각 |

`status`는 저장하지 않고 조회 시 계산합니다. paused는 STOPPED 우선, 그 외 기간 끝/현재 예산의 유효 차단은 ENDED이고 나머지 RESERVED/ACTIVE입니다. end_reason은 읽기 전용 계산값입니다. 집계 원장은 가짜 사용량이나 실잔액 카운터로 대체하지 않습니다.

현재 구현은 제목·이미지·링크가 바뀌면 새 creative_version을 생성하고 변경 전 감사 snapshot을 보존합니다. 옛 배달의 새 표시/변경 이후 발생은 차단하고 변경 전 당시 유효 발생은300초 내 검사합니다. 위치/일정은 별도 검사, priority는 다음 선정부터 적용하며 반복 창과 최초 응답은 유지합니다.

### 3.3. `ad_assets` — 이미지 원본

| 필드 | 타입·필수 여부 | 규칙 |
|---|---|---|
| `_id` | string · 필수 | API의 `asset_id` |
| `image_bytes` | BSON Binary · 필수 | 업로드 이미지 원본 바이트 |
| `mime_type` | string · 필수 | 실제 디코딩 결과의 PNG/JPEG/WebP MIME |
| `byte_size` | integer · 필수 | 실제 바이트 길이, 1~2,000,000 |
| `width`, `height` | integer · 필수 | 디코딩한 양수 픽셀 정보 |
| `sha256` | string · 필수 | 원본 SHA-256 hex; 동일 파일 진단용 |
| `uploaded_by_account_id`, `identity_source` | string · 필수 | 서버에서 검증한 업로드 관리자 |
| `schema_version`, `is_test`, `created_at` | 공통 타입 · 필수 | 서버 설정·시각 |

정적 WebP/JPEG/PNG만 허용합니다. 확장자·클라이언트 MIME만 믿지 않고 디코딩·애니메이션 여부·실제 크기와 BSON 전체 문서 크기를 검사합니다. 2,000,000bytes는 허용하고 1byte 초과는 거부합니다. 권장 해상도와 다르다는 이유만으로 유효 이미지를 거부하지 않습니다.

이미지 교체는 새 asset을 만들며 기존 바이트를 덮어쓰지 않습니다. SHA-256을 광고 병합 키나 관리 요청의 멱등키 대신 사용하지 않습니다. 목록 JSON에 원본 바이트를 넣지 않고 관리 인증 또는 공개 delivery proof·현재 게시 자격 검사를 거쳐 제공합니다. 공개 주소는 `ADS_PUBLIC_BASE_URL`로 연결하고 응답은 no-store입니다. 운영 주소·전달 인프라·미사용 이미지 정리/백업은 별도 인계입니다.

### 3.4. `ad_admin_changes` — 감사와 성공 멱등 응답

| 필드 | 타입·필수 여부 | 규칙 |
|---|---|---|
| `_id` | string · 필수 | `log_id` |
| `operation` | string · 필수 | `UPLOAD_ASSET` / `CREATE` / `UPDATE` / `STOP` |
| `ad_id` | string 또는 null · 필수 | 업로드는 null, 광고 변경은 필수 ID |
| `asset_id` | string · 필수 | 업로드 ID 또는 변경 당시 광고의 소재 |
| `identity_source`, `actor_account_id` | string · 필수 | 검증된 관리자 |
| `resource_scope` | string · 필수 | 생성 `ads:create`, 업로드 `assets:upload`, 수정/중단 해당 ad_id |
| `idempotency_key_hash`, `request_hash` | string · 필수 | 멱등키 hash와 허용 입력의 정규 본문 hash |
| `changed` | boolean · 필수 | 실제 업무 변경 여부 |
| `version_before`, `version_after` | integer 또는 null · 필수 | 광고 변경 전/후 version; 업로드는 null, 새 광고 이전은 null |
| `before_snapshot` / `after_snapshot` | object 또는 null / object · 필수 | 신규 작업의 이전 값은 null; 당시 허용 설정/메타데이터만 보존 |
| `reason` | string 또는 null · 저장 필수 | 서버 작업 사유/기존 허용 입력; 새 필수 화면 입력으로 만들지 않음 |
| `response_snapshot` | object · 필수 | 최초 성공 HTTP 상태와 응답 본문 |
| `completed_at`, `occurred_at` | Date · 필수 | 완료/업무 변경 시각 |
| `retention_due_at` | Date 또는 null · 저장 필수 | 양쪽 보관 의무와 pending/참조 보호를 고려한 정리 후보 시각; 정리 작업 미구현으로 현재 null |
| `log_relay` | object · 필수 | 아래 PostgreSQL 로그 전달 보조 상태 |
| `schema_version`, `is_test`, `created_at` | 공통 타입 · 필수 | 서버 설정·시각 |

등록/수정/중단 snapshot에는 title·asset·creative_version·URL·위치·기간·priority·paused·stopped_at·version을 보존합니다. 업로드 snapshot에는 asset ID·MIME·크기·픽셀·해시를 보존합니다. 이 내용은 이후 광고가 수정되어도 덮어쓰지 않습니다.

이미 중단된 광고를 같은 상태로 저장하는 등 무변경 요청은 `changed=false`로 성공 응답을 보존하되 version·updated_at·실제 변경 건수를 증가시키지 않습니다. 동일 멱등 요청 재전송은 새 감사 문서를 만들지 않습니다. 업로드/광고 생성은 각각 새 asset/광고를 한 번만 만듭니다.

### 3.5. 최소 인덱스

| 컬렉션 | 인덱스 | 목적 |
|---|---|---|
| 모든 컬렉션 | `_id` unique | 업무 ID 중복 방지 |
| `ads` | `(placement, paused, priority, starts_at, ends_at)` | 후보 조회; 실제 정렬 방향·성능은 실행계획으로 검증 |
| `ads` | `(updated_at, _id)` | 안정적인 관리 목록 정렬 |
| `ad_admin_changes` | `(ad_id, occurred_at)` | 광고별 감사 조회 |
| `ad_admin_changes` | unique `(identity_source, actor_account_id, operation, resource_scope, idempotency_key_hash)` | 관리 요청 중복 방지 |
| `ad_admin_changes` | `(log_relay.status, log_relay.next_retry_at)` | 미전달 로그 재시도 조회 제안 |

asset의 sha256 비유일 인덱스는 진단 조회가 필요할 때만 추가합니다. TTL 자동 삭제는 첫 단계에 적용하지 않습니다. 감사·멱등 결과·미발행 로그·공유 asset 참조를 먼저 검사해야 하며, unique 인덱스만으로 모든 업무 조건이 해결되지는 않습니다.

## 4. 관리 로직과 원자 저장

### 4.1. 상태와 동시 수정

```text
if paused:                 status = STOPPED
elif now >= ends_at:       status = ENDED  # PERIOD_ENDED
elif current_budget_block: status = ENDED  # BUDGET_EXHAUSTED
elif now < starts_at:      status = RESERVED
else:                      status = ACTIVE
```

수정과 중단은 요청 본문의 `version`을 필수로 받습니다. MongoDB 조건 갱신은 `_id`와 기대 version을 함께 검사하며, 오래된 version은 `VERSION_CONFLICT` / 409입니다. 순서만 맞춘 read-then-write로 동시 수정 문제를 해결하지 않습니다. 일반 PUT은 `paused`와 `stopped_at`을 서버의 기존 값으로 유지합니다. 재개 방식은 미정입니다.

예산 `daily_budget_tokens`/`total_budget_tokens`는 함께 입력하는 선택 쌍이며 두 값 모두 strict 양의 int64, 명시 null은 거부합니다. 생략한 신규 광고는 null 두 값/budget_version으로 저장 가능하지만 운영 제공 부적격입니다. 수정 생략은 유지, 두 값 실제 변경에만 새 UUID budget_version을 부여합니다. 무변경·소재/일정/priority 편집은 예산 버전을 유지하며 기존 관리 감사/멱등 트랜잭션을 사용합니다. 금액 기본값을 만들지 않습니다.

배치가 쓰는 budget_blocked_at/until/version/scope는 선택 기술 필드이며 관리 version·actor는 바꾸지 않습니다. 현재 budget_version과 일치하고 차단 구간이 현재 유효할 때만 budget ENDED입니다. end_reason은 읽기 전용 계산값 BUDGET_EXHAUSTED/PERIOD_ENDED/null이며 paused는 별도 유지합니다.

### 4.2. 등록·수정·중단·업로드 공통 처리

1. 공통 환경에서 현재 활성 ADMIN·광고 권한과 Origin/CSRF를 확인합니다. 인증 서비스 장애는 관리 변경을 차단합니다.
2. 허용 입력·strict 타입·기간·URL·이미지·필수 멱등키를 검사합니다. 클라이언트가 owner/role/계정 ID·version 결과·운영 환경을 정하게 하지 않습니다.
3. 같은 멱등 범위의 최초 성공 기록을 확인합니다. 같은 정규 본문은 원래 HTTP 상태/응답, 다른 본문은 `IDEMPOTENCY_CONFLICT` / 409입니다. 저장된 성공 응답은 version 재검사보다 먼저 반환합니다.
4. 새 수정/중단이면 현재 version과 대상 asset을 검사하고 광고 문서에 실제 쓰기 잠금을 얻습니다. 적용 시각은 잠금 이후 트랜잭션 안에서 다시 정하므로 요청 대기 시각을 과거 이력으로 소급하지 않습니다. 이는 업무 효력 시각이며 MongoDB 물리 commit timestamp가 아닙니다. ID·정규 요청 hash는 재시도에서 유지하고, 성공 커밋의 응답·snapshot·로그는 같은 적용 시각을 사용합니다.
5. 같은 MongoDB 트랜잭션으로 `ads` 또는 `ad_assets`의 업무 변경과 `ad_admin_changes`의 감사·멱등 원응답·`log_relay`를 커밋합니다.
6. 커밋 성공 후 응답합니다. 실패에는 부분 저장이나 성공 응답이 없으며, 응답 유실·커밋 결과 불명확 시 새 ID를 만들어 다시 등록하지 않습니다. 동일 멱등키/commit 결과를 조회해 해결합니다.

저장 성공 이후 PostgreSQL 로그가 지연되더라도 커밋된 업무 결과는 유지합니다. MongoDB 트랜잭션 내부에서 외부 인증 호출·PostgreSQL 쓰기·파일/네트워크 전송을 실행하지 않습니다. standalone mongod는 이 다중 문서 원자 저장의 완료 환경으로 보지 않습니다.

### 4.3. `log_relay`와 PostgreSQL 사본

ADS05의 기술 보완 기준을 적용하며 별도 outbox 컬렉션을 첫 단계에 추가하지 않습니다.

| 보조 필드 | 의미 |
|---|---|
| `log_event_id` | log_id에서 안정적으로 정한 string; 같은 업무 로그의 재전송 ID |
| `payload`, `payload_hash` | 당시 작업/관리자/광고/asset·changed/version·request_id·is_test; 불변 |
| `status` | `PENDING` / `SENT` |
| `attempt_count` | 전달 시도 횟수, 정수 |
| `next_retry_at`, `last_error` | 다음 재시도 시각/오류, 필요 없는 때 null |
| `sent_at` | PostgreSQL 저장 확인 시각 또는 null |

relay는 PostgreSQL의 `UNIQUE(log_event_id)`에 같은 payload인지 확인하고 저장한 다음 MongoDB 보조 상태를 SENT로 바꿉니다. PostgreSQL 저장 후 SENT 전 종료되면 같은 ID로 재전송합니다. 같은 ID의 다른 payload는 경보이며 덮어쓰지 않습니다. 장애에는 PENDING을 유지하고 재시작 후 전달합니다.

현재 relay는 attempt_count와 next_retry_at의 조건부 claim/완료 처리로 만료된 작업자의 ACK가 새 작업을 덮지 않게 합니다. claim/재시도 간격은 전달 작업자의 기술 설정이며 운영 배치 주기를 확정하는 값이 아닙니다. relay 상태 변경으로 감사 snapshot/최초 멱등 응답을 바꾸거나 광고 지표·예상 토큰을 재산출하지 않습니다. PENDING 자료는 감사 기간이 지나도 먼저 삭제하지 않습니다.

관리 목록은 updated_at/_id 내림차순, 기본20/최대100과 필터에 묶인 서명 커서로 구현했습니다.
summary는 실제 상태별 광고 수/오늘 측정값, 목록 행 measurement는 보존 범위 누적을 반환합니다. as_of·aggregation_status·coverage·coverage_from/coverage_through·is_stale로 실제 집계 근거/지연을 표시하며 미연결 null/PENDING과 실제0을 구분합니다. OpenAPI와 API 테스트가 필드명 기준입니다.
`GET /api/admin/ad-assets/{asset_id}`는 관리 미리보기용 인증 이미지 조회입니다. 공개 이미지는 아래 delivery 기반 경로로 제공하며 asset ID만으로 공개하지 않습니다.

공통 `/api/auth/login`, `/api/auth/me`, `/api/auth/logout`는 공통 환경의 기존 경계를 사용합니다. 광고 권한으로 음악 검수·피드백 원본까지 열지 않으며, 통합 메뉴와 역할별 접근은 각 API에서 검증합니다. 로그아웃은 광고 중단이 아닙니다.

운영 guest/주소·서명·로그 sink·상시 watch와 브라우저·인프라 연결은 코드 완료와 구분합니다.

### 6.1. 공개 제공

`GET /api/ads`는 위치·기간·paused·사용 가능한 이미지·예산 자격을 검사합니다. 가장 높은 priority의 후보를 ad_id 코드 포인트 순서로 위치별 round-robin하며 top/bottom 커서를 구분합니다. 새 delivery 발급과 커서 갱신은 같은 트랜잭션입니다. 재확인·미리보기·멱등 재전송은 커서를 진행하지 않습니다.

제공과 중단은 광고 문서의 version 조건 실제 쓰기/복원으로 직렬화하고, 경합 시 새 snapshot에서 후보를 다시 확인합니다. 기존 delivery 재확인은 primary의 현재 상태와 명시 정책을 읽고 `valid_until <= min(evaluated_at + 3초, 당시 ends_at, 현재 ends_at, display_expires_at)`을 반환합니다. 공개 화면 담당자는 1초 재확인과 통신 실패/기한 만료 숨김으로 중단 커밋부터 정상 활성 화면 3초 이내 숨김을 검증합니다.

공통 guest는 최초 상단 조회에서 광고가 없어도 발급/재사용합니다. 하단·측정은 이 문맥을 이어받으며 로그인·지역 선택·추천 요청을 조건으로 하지 않습니다. 쿠키 저장 불가에도 표시/클릭 이동은 유지하고 측정은 `MEASUREMENT_UNAVAILABLE`로 운영 집계에서 제외합니다.

| 구현 경로 | 추가 입력/반환 |
|---|---|
| `GET /api/ads` | placement 필수, delivery_id 재확인에 `X-Ad-Delivery-Token`; 신규 재전송에 선택 `Idempotency-Key` |
| `POST /api/ad-events` | 네 이벤트 본문 필드와 필수 `X-Ad-Delivery-Token` |
| `GET /api/ad-deliveries/{delivery_id}/image` | query delivery_token으로 proof·현재 게시 자격 검사 후 이미지 원본 |

필수 설정은 `ADS_GUEST_CONTEXT_PROVIDER`, `ADS_PUBLIC_POLICY_PROVIDER`, `ADS_DELIVERY_SIGNING_KEY`,
`ADS_PUBLIC_BASE_URL`입니다. guest provider는 공유 서비스가 검증한 `PublicGuestContext`를 반환하고,
policy provider는 `domains.ads.runtime_policy.get_public_policy`로 명시 연결합니다.1800초·split_deadlines=True·check_budget_history=True·cap_at_midnight=False이며 `.env.example`에 경로를 기록했습니다. 실제 `.env` 비밀/공유 서비스 설정은 별도입니다.
이미지 읽기는 guest를 발급하지 않고 proof와 정책을 확인합니다. 미설정/오류는 503으로 차단합니다.
정책 callback은 트랜잭션 안에서 재실행될 수 있으므로 외부 API·PostgreSQL·파일·네트워크 I/O를 금지합니다.
정확한 함수 인계는 [공개 API 인계](./공개_선정과_측정_로직_인계.md#12-운영-연결-전-필수-설정)를 따릅니다.

### 6.2. 최초 측정 판정

`POST /api/ad-events`의 허용 본문은 delivery_id·event_id·event_type·occurred_at입니다. 불투명 delivery 검증 자료는 `X-Ad-Delivery-Token`으로 별도 전달합니다. 광고/소재/위치/owner/인정 여부/토큰/is_test는 서버 문맥에서 결정합니다. 측정 POST의 Origin/CSRF를 본문 해석 전에 검사합니다.

처리 순서는 동일 event_id/본문의 저장 응답 → 문맥·delivery·발생/수신·당시 유효성 → delivery/type 최초 소비 → 반복 창 → 원자 저장입니다. 노출/클릭마다 delivery별 한 번만 소비하며, 억제된 delivery도 반복 창 종료 후 새 event_id로 다시 인정하지 않습니다.

| 판정 항목 | 적용 기준 |
|---|---|
| 노출 | 이미지 로딩 완료·활성 탭·면적 50% 이상·연속 1초; 조건 중단 시 타이머 초기화 |
| 새 delivery 반복 | `(owner_guest_id, ad_id, placement, event_type)` 기준 노출 60초·클릭 300초 |
| 반복 기준 시각 | 서버 최초 인정 `accepted_at`; 억제/중복은 창을 연장하지 않음 |
| 지연 | 미래 occurred_at 제외; `0 <= received_at-occurred_at <= 300초` |
| 중단/종료 전 보고 | 당시 유효하고 5분 이내 수신하면 검사; 이후 발생은 제외 |
| 집계일 | 검증된 occurred_at을 Asia/Seoul로 변환한 날짜 |
| 주요 결과 | COUNTED, DELIVERY_DUPLICATE, REPEAT_SUPPRESSED, LATE_EVENT, DELIVERY_INVALID, MEASUREMENT_UNAVAILABLE |

측정 원본·delivery/type 최초 claim·반복 창·최초 응답·인정 시 예상 토큰 항목·PENDING 로그를 같은 광고 MongoDB 트랜잭션에 저장합니다. 같은 event_id 재전송은 원응답을 재반환하고 판정·반복 창·마지막 수신 시각을 연장하지 않습니다.

| 공개 추가 컬렉션 | 최소 상태와 동시성 |
|---|---|
| `ad_rotation_state` | 위치/환경별 last_ad_id·revision CAS |
| `ad_deliveries` | 불변 광고 snapshot·issued/만료·정책 version·token hash·원응답·내장 claims·마지막 사용/신규 수신 |
| `ad_events` | event_id 최초 판정·정규 요청/원응답·발생/수신/처리·KST일·내장 log_relay |
| `ad_repeat_windows` | guest/ad/placement/type/환경별 accepted_at·revision CAS |
| `ad_estimated_usage_ledger` | unique event_id·당시 예상 단가/사용량·`ESTIMATED` |

공개 스키마 버전은 `phase3-ads-public-20261015.1`입니다. 배달 멱등키는 선택된 문자열 hash에만
소유/위치/환경 고유 인덱스를 적용합니다. claim/outbox/ad_versions·사용자 컬렉션을 별도로 만들지 않습니다.
당시 광고 상태는 `ad_admin_changes.after_snapshot`의 발생시각 이하 최신 변경 시각/version을 사용합니다.
관리·측정 로그는 `relay_ads_logs`·`relay_ads_event_logs`에서 기존 durable `ADS_LOG_SINK`로 전달하며
최초 소진 로그는 `relay_ads_budget_logs`가 같은 durable hook로 전달하며 실제 PostgreSQL sink 연결을 완료한 것은 아닙니다.

### 6.3. 주기 통계와 예산

| 인정 이벤트 | 예상 사용량 |
|---|---:|
| top 유효 노출 | 8토큰 |
| bottom 유효 노출 | 5토큰 |
| 인정 클릭 | 추가 15토큰 |

정상 노출 후 클릭은 top 23/bottom 20, 노출 조건 전 클릭은 15토큰입니다. 클릭을 노출로 자동 추가하지 않습니다. 중복·억제·미리보기/테스트는 운영 비용을 만들지 않으며 실제 잔액 차감·구매·환불은 수행하지 않습니다.

최초 예상 원장에는 event/delivery·광고/소재/위치·종류·발생/처리·KST일·정책 버전·적용 단가·사용량과 `ESTIMATED` 상태를 보존합니다. 불변 인정 항목만 저장하며 실제 청구/정정 원장을 구현하지 않았습니다. 후속 배치는 이 항목의 합계를 갱신하고 재실행 중복을 막아야 합니다. 지연 이벤트는 원래 KST 발생일에 속하며 현재 단가로 과거 기록을 재산출하지 않습니다.

관리 통계와 예산 검증은 모두5분입니다. 원장 대상 범위를 재계산해 ad_daily_metrics를 교체하고 지연 보고의 발생일도 보완합니다. budget_version별 일일/전체 원장 합계가 한도 이상이면 최초 cutoff를 고정하고 이후 신규/재확인/이미지를 차단합니다. occurred_at < cutoff인 당시 유효 보고는300초 내 초과 인정하고 경계 이상은 제외합니다. 최소잔여23/20·예약은 채택하지 않았으며 다음 검증 전 초과할 수 있습니다.

배달 표시30분·광고 종료 단축과 추가300초 보고 마감을 분리합니다.30분 만료는 재발급, 캠페인 자동 종료는 소진/게시 기간 두 가지이며 수동 paused는 자동 해제하지 않습니다. 제목/이미지/링크 수정은 새 creative_version과 옛 배달 이후 표시/발생 차단, 이전 발생은 당시 snapshot 검사입니다. 기존 배달/원응답을 늘리거나 예산 정책 marker 없는 기록에 소급하지 않습니다.

새 ad_budget_states/ad_daily_metrics를 포함해 총10개 컬렉션입니다. apply_ads_policy_schema는 dry-run 기본/--apply local `_dev` guard, refresh_ads_policy는1회 기본/--watch300초 시작간격, relay_ads_budget_logs는 최초 소진 로그 전달입니다. runtime 상태 누락은 부적격,300초 초과 stale/future/형식 오류는503 기술 장애이며 새 캠페인 종료가 아닙니다. 실제 watch·공유 guest/PG·HTTPS·AWS/브라우저는 미실행입니다. 일일KST는 기존 발생일 정렬에 맞춘 개발 기준이며 cap_at_midnight=False, 실예산값 기본 없음입니다.

## 7. 보관·인계·검증

광고 관리 변경 이력은 occurred_at부터 365일입니다. 감사와 성공 응답을 겸하는 문서는 감사/멱등의 양쪽 보관 의무와 pending 보호가 끝난 뒤 정리합니다. 무변경 요청 결과·멱등키 재사용 기간·이미지/백업 보관은 미정입니다. 측정 원본은 received_at부터 90일, delivery는 마지막 실제 사용/신규 수신 기준 90일, 예상 원장은 processed_at부터 365일인 기존 계약을 유지합니다. 집계는 별도 계약 기산점부터 365일입니다. pending/공유 참조 보호를 포함한 정리 작업은 미구현이므로 삭제 예정 시각을 계산하지 않고 retention_due_at은 null로 둡니다. 자동 TTL은 설정하지 않습니다. 광고 보관 기간을 공통 계정/음악/날씨에 적용하지 않습니다.

| 미정/필요 인계 | 영향 | 담당 |
|---|---|---|
| 제목 길이·priority 범위·일정 입력 세부 | 최종 입력 validator | PL·광고 로직 담당 |
| 공통 ADMIN 검증·현재 권한/회수·CSRF·광고 프로세스 라우팅 | 실제 관리 API 연결 | 공통 인증 담당·INF |
| MongoDB/드라이버 버전·replica set·권한·접속·복구 | 다중 문서 원자성/환경 검증 | INF·광고 로직 담당 |
| 공개 주소/라우팅·이미지 전달 인프라·미사용 정리·백업 | 구현한 proof 이미지 경로의 실제 운영 연결 | INF·화면 담당·광고 로직 담당 |
| 배달30분/소재교체의 브라우저 실연결 | 확정 정책의 표시/보고·3초 숨김 검증 | 공개 화면 담당·광고 로직 담당 |
| 실예산 두 값·재개 API/실권한·상시 배치 실행 |5분 검증/통계·cutoff는 확정, 운영 값/환경 인계 | PL·INF·광고 로직 담당 |
| 로그 claim/lease·보관/멱등키 만료·공통 계약 버전 차이 | relay·정리·응답 표준 | 공통 백엔드·INF·광고 로직 담당 |

개발 검증은 먼저 예약/게시/종료/중단 경계, 중단 후 PUT 유지, version 동시 충돌, 같은 멱등키/동일·다른 본문, 정적 이미지 2MB 경계/위장 형식, MongoDB 커밋 실패/응답 유실, PostgreSQL 저장 후 SENT 전 종료를 확인합니다. 태그 필드 포함 요청은 거부하고, 미연결 통계와 실제 0을 구분합니다. 구체 사례는 [ADS03 V01~V41](../../handoff/ads/03_광고_인프라와_검증_인계.md)를 사용합니다.
