## 문제와 변경 전 동작

작업자는 검증된 압축 카탈로그를 프로세스에서 재사용했지만 매 요청마다 전 곡을 순회해 공통 적격성·선호 점수를 다시 확인했습니다. 장르가 지정된 규칙 선곡은 CP-SAT에서 장르 대표 변수와 품질·동점 목적을 처리했으며, 후보 수가 많아지면 같은 마감 시간 안에 탐색을 끝내지 못할 수 있었습니다.

## 변경한 코드와 호출 흐름

1. `worker.run_one` → `_collect_candidates`가 저장된 Job의 고정 context를 전달합니다. `allowed_genre_group_codes`, `allowed_speed_codes`, `excluded_track_ids`, 보컬 옵션을 입력 그대로 적용합니다.
2. `_index_for`는 `(catalog.pk, catalog.sha256, POLICY, MAPPING, WEATHER_SCORE_VERSION, OFF_SCORE_VERSION)` 기준으로 `CandidateIndex` 한 개를 작업자 프로세스에서 재사용합니다. 인덱스는 검증된 카탈로그에만 만들며 날씨별 사전 점수의 유효 버전을 확인합니다.
3. 후보 인덱스는 공통 적격 곡 수를 먼저 세고 ON 공통 후보가 `max(1, min(5000, catalog_count // 10))`보다 작을 때만 해당 요청을 압축 비트셋으로 좁힙니다. 넓은 후보와 OFF 요청은 기존 전체 순회로 처리합니다. 오래되거나 빠진 점수 캐시는 인덱스에서 제외 근거로 쓰지 않고 기존 `policy.score` 계산에 맡깁니다. 후보 ID·점수·감사 집계는 기존 경로와 동일해야 합니다.
4. `solver._solve_window`는 선택 장르가 있는 요청에만 `exact_search.solve_window`를 연결합니다. 증명 가능한 정확 탐색 단축을 먼저 시도하고 한도에서 거절되면 `_solve_window_fallback`의 CP-SAT 경로를 사용합니다. 태그가 없는 요청은 기존 solver 경로에 바로 들어갑니다. 모든 단계는 요청의 동일한 절대 마감 시각을 공유합니다.
5. CP-SAT 장르 대표 변수 생성과 품질 목적 계수, 30개 단위 동점 비교를 간소화했습니다. 분수 점수, 정수 duration_ms, 176~184분 범위, 장르 100%→80% 우선순위, seed/ID 재현 순서는 그대로 둡니다.

`matching.representatives`는 기존 결정적 장르 대표 매칭을 solver와 exact search가 공유하는 모듈로 옮겼습니다. `choose_preview`와 Gemini의 후보 제안/검증 계약은 변경하지 않았습니다. HTTP/API 입력·응답, 모델, migration, 환경변수, 작업 상태 코드, 저장 스키마, 점수 버전은 변경하지 않았습니다. 새로운 외부 라이브러리도 추가하지 않았습니다.

## 변경 파일

| 파일 | 실제 연결 |
|---|---|
| `backend/recommendation/candidate_index.py` | 카탈로그 비트셋, 상속 필터·제외·보컬·날씨 사전 점수 후보 게이트 |
| `backend/recommendation/worker.py` | 버전별 인덱스 수명, 좁은 ON 후보에 대한 선택 적용, 기존 감사 집계 보존 |
| `backend/recommendation/exact_search.py` | 정확 시간/품질/대표 제약 단축 및 제한 시 CP-SAT 대체 경로 |
| `backend/recommendation/matching.py` | 기존 대표 매칭의 공통 정의 |
| `backend/recommendation/solver.py` | 정확 탐색 래퍼, 개선된 CP-SAT 변수·목적 구성 |
| `backend/recommendation/tests/test_candidate_index.py` | 상속 필터·점수·감사·부분/구버전 캐시·보컬 precedence 대조 |
| `backend/recommendation/tests/test_exact_search.py` | 태그 분기·대표·80% 비율·동점 seed 결과를 CP-SAT 대체 경로와 비교 |

## 검증 결과

- 표적 Django 검사: 후보 인덱스·정확 검색·기존 추천 정책 테스트 **42건 통과**, Django system check 오류 없음.
- 기존 추천 정책·탐색 부족 검사까지 포함한 표적 검사: **50건 통과**.
- 실제 CSV 로컬 대조: 원본 89,740개 ID 중 무효 1개·중복 상충 0개, GENERAL 곡 **86,485개**. ON 기본·ON 태그/속도/무보컬·OFF 테마·OFF 장르/빠르기 4조건에서 후보 ID·정확 점수·모든 감사 집계가 전체 순회 기준과 같았습니다.
- ON 태그 표본은 공통 후보 7곡에서 날씨 탈락 2곡, 최종 5곡으로 일치했습니다. 후보 생성 구간 기준 전체 순회 중앙값은 약 **0.122초**, 인덱스 재사용 뒤 두 번의 실행은 **0.6ms 안팎**이었습니다. 첫 인덱스 사용은 약 14ms였으며 카탈로그 인덱스 빌드는 약 0.21초/비트셋 324,330바이트였습니다.
- 넓은 후보의 실험 인덱스 경로는 기존 순회보다 느린 사례가 있어 작업자에서 비활성화했습니다. 기본 조회 속도 추가 개선은 이번 범위에서 보류합니다.

CSV 대조는 로컬 정규화·일반 후보 판정·점수 전처리 후 후보 생성 함수만 비교한 결과입니다. 전체 선곡 작업시간, PostgreSQL I/O·메모리, 동시 worker, AWS 응답 P95, 브라우저 결과 표시는 측정하지 않았습니다. P95 2.5초는 계속 목표이며 달성값으로 보고하지 않습니다. 전체 백엔드 회귀와 GitHub 환경 검증 결과는 커밋 직전에 갱신합니다.

## 캐시·저장·복구 영향

인덱스는 작업자 프로세스 메모리에서만 재생성할 수 있는 파생 자료입니다. DB에는 인덱스나 추가 점수를 쓰지 않습니다. 다른 catalog id/hash 또는 정책·매핑·점수 버전이 오면 이전 인덱스를 재사용하지 않고 새로 생성합니다. 무결성 검증 실패는 기존 `CATALOG_INVALID` 처리 흐름을 따릅니다. 인덱스 관련 예외가 발생해 Job 결과/부모 snapshot을 덮어쓰지 않도록 기존 worker 오류 처리를 유지합니다.

복구는 해당 기능 브랜치의 이전 커밋으로 되돌리면 됩니다. schema/data migration이나 별도 캐시 삭제 작업은 없습니다.
