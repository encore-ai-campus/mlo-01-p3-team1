PG 전용 테스트는 두 독립 연결에서 같은 작업 선점1회, 잠긴 작업 건너뛰기, Gemini 공통 점유 상한, 공통 시작 간격, 두 API의 큐 상한 경합을 검증합니다. 별도 프로세스 검사는 한 워커가 작업 두 개를 연속 수행해 분산처럼 보이는 상황을 막기 위해 계산 진입을 동기화하고 실제 규칙 solver를 각각 실행합니다. 시간 측정을 위한 부하 시험은 아닙니다.

복구 검사에서는 lease 만료를 시험 시각으로 앞당겨 token 변경·이전 워커 갱신 거절·복구2회 후 실패를 확인합니다. 외부 호출은 시험 대역으로 예약만 검사하며, 시작 후 불확실한 Gemini 작업의 재호출 차단·예약 유예와 rule 진행을 확인합니다. SIGTERM 검사에서는 등록한 신호 핸들러를 호출해 현재 작업 이후 새 선점을 중단하는 동작을 확인했습니다. Linux systemd의 실제 SIGTERM/강제 종료·EC2 fencing 시험과 구분합니다.

전체 검사에서 기존 카탈로그 migration 시험이 종료 후 schema를0005에 고정 복원해 새 Job 필드가 사라지는 문제가 발견됐습니다. 복원을 현재 leaf migration으로 바꾼 뒤 전체297개와 PG37개를 다시 통과했습니다. migration 자체의 과거 Catalog 불변 보존·backfill 기대값은 유지합니다.

API2프로세스의 초기 Windows 실행에서는 한 자식이 소켓 listen의 WinError10022 뒤 재기동했습니다. 당시 HTTP 추천2개는 완료됐으나 안정적인 API2프로세스 통과로 보고하지 않습니다. 최종 실행 예시는 Control당 API1개로 정리했고 HTTP 전 과정을 다시 통과했습니다. A/B 호스트 간 API 분산·ALB·Linux API 증가는 실제 환경에서 확인해야 합니다.

## 미검증·인계

시험 추천은 합성64곡 고정 자료를 사용하고 is_test 표시를 유지했습니다. 실제 CSV 카탈로그·86,485곡 메모리 peak·동시 이용자 수·P95 목표·T3 credit·PG 최대 연결/복구·ALB/HTTPS/SSO·실제 Gemini 요금/할당량·실제 날씨·Control fencing은 미검증입니다. 이 결과로 운영 처리량이나 HA 완료를 선언하지 않습니다.

배포 시 양쪽 호스트를 같은 코드·DB·한도로 맞추고 구 워커를 drain한 뒤 migration을 적용합니다. [환경/서비스 예시](../../config/environments/recommendation/README.md)와 [인프라 수용 항목](../runbook/추천_분산처리_인프라_인계.md#7-관측과-수용-기준)을 따릅니다. 사용자의 후속 요청에 따라 별도 브랜치/PR 없이 develop에 직접 commit/push합니다. 실제 서버 설치·활성화는 수행하지 않았습니다.
