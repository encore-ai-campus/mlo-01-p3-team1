## 2. 음악 RDB4개와 불변 카탈로그

음악 담당의 [테이블 설계](../handoff/music/테이블_구조_설계.md)를 우선합니다. music_track·music_album·music_tag·track_tag가 곡 기본4개입니다. 추천·표시18개와 instrumental_review_value를 구분하고 FK/UNIQUE·활성/승인 연결·곡당 한 행 집계를 적용합니다. DB 제품/물리DDL/접속은 별도 환경 검증이며 공통 PostgreSQL 선택으로 자동 확정하지 않습니다.

1. 원본CSV는 로컬/S3 보관 가능하며 source/schema/version·해시·원본 행/고유 곡 수·오류를 기록합니다. 원본과 결과19개 입력을 구분하고 변환은 원본에서만 수행합니다.
2. 곡/앨범/태그/연결 적재는 음악RDB의 트랜잭션·FK/UNIQUE로 검사합니다. 일반 upsert는 확정 검수값을 보존하고 검수 변경은 별도 작업으로 수행합니다.
3. 태그를 종류별로 먼저 집계해 music_recommendation_view에서 곡당 한 행·18개·genre_group_codes를 제공합니다. 활성/approved 연결만 공개 조회에 사용하고 원본 연결은 보존합니다.
4. 검증된 조회 결과를 catalog_version별 불변 스냅샷으로 고정합니다. 정확한 물리 발행/내보내기 형식·manifest·접속은 C/B/INF가 확정합니다. S3는 보관/내보내기 수단일 수 있으며 음악 기준 저장을 대신하지 않습니다.
5. 검증/전체 읽기 완료 후 공통 PostgreSQL의 catalog_snapshot/READY 포인터를 전환합니다. 음악RDB와 업무DB가 다르면 두 DB의 원자 동시쓰기를 가정하지 않고 완료된 불변 자료를 먼저 준비합니다. 실패 시 현재 정상 포인터를 보존합니다.
6. 작업은 카탈로그/정책/사이클/당시 값·해시를 고정하고 검증된 조회 모델로 규칙/Gemini에 같은 적격 목록을 제공합니다. 사용자 요청마다 Spark/원본 전체를 스캔하거나 최신 테이블로 과거 스냅샷을 바꾸지 않습니다.

검수 이력·카탈로그 버전/발행 감사·결과/제외/평가/정책은 음악 기본4개와 별도 운영 자료입니다. 정확한 제품/DDL·물리 경계·백업/보관은 인계 사항입니다. 3차 음원 파일·직접 재생·Spotify API 필수 연동은 추가하지 않습니다.

## 3. PostgreSQL 로그·피드백의 원자성/재처리

결과/제외/평가/승인 상태와 feedback_event·당시 context/곡·outbox·멱등 응답은 기존 PostgreSQL 트랜잭션으로 유지합니다. Kafka relay는 같은 event_id를 발행하고 Spark는 원본/정제/집계를 PostgreSQL에 멱등 반영합니다. PostgreSQL 원본 단계는 source_domain·topic/partition/offset·payload·수신/처리 시각·is_test를 기록하며 offset 적재 대조/경보를 유지합니다.

온라인 업무 feedback_event와 파이프라인 원본 기록의 역할을 구분하고 같은 DB에 있다는 이유로 발행/수신 확인을 생략하지 않습니다. 원본 단계의 고유 키는 stream/partition/offset 또는 안정적 배달 ID, 정제는 event_id·대상 revision입니다. 평가 취소/역순/중복·선택 태그와 곡 태그·당시 값·보관 중 스냅샷을 유지합니다. PostgreSQL 원본/정제/집계는 별도 스키마/권한/인덱스·pool/timeout으로 조율합니다.

재처리는 Kafka 보관 범위 또는 확인된 PostgreSQL 원본에서 별도 출력/실행 ID로 수행하고 최초 ID/판정·revision을 보존해 결과를 대조합니다. Spark checkpoint는 실행 상태이며 로그 기준 저장소가 아닙니다. Kafka와 PostgreSQL 양쪽 원본이 없는 구간은 복구 불가입니다. 과거 Delta 제안이나 옛 검증 기록을 현행 구현 완료로 표시하지 않습니다.

광고 업무 로그는 ad_admin_changes·ad_events·최초 소진 ad_budget_states의 log_record에 같은 MongoDB 트랜잭션으로 저장합니다. 공통 PostgreSQL 로그 테이블/발행은 사용하지 않습니다. 과거 log_relay는 보존하며 외부 전달을 재개하지 않습니다. 상세 컬렉션/원자성/보관은 [ADS 저장 계약](../handoff/ads/02_광고_MongoDB_저장과_로그_연결.md)을 따릅니다.

### 3.1. 광고 공개 측정과5분 통계/예산

2026-10-15 사용자 결정의 수명/소재/통계/예산 동작은 [공통 개발 계약3.8절](./3차_공통_개발_계약과_검증_기준.md)을 적용합니다. 광고 MongoDB의 현재 명시 범위는 아래10컬렉션이며 초기 관리3개와 공개 측정5개, 이번 정책2개의 단계 구분을 유지합니다.

| 단계 | 컬렉션 | 원자 저장/조회 경계 |
|---|---|---|
| 초기 관리3 | ads / ad_assets / ad_admin_changes | 광고·MongoDB 이미지 Binary·감사/성공 멱등 응답·관리 내부 log_record |
| 공개 측정5 | ad_rotation_state / ad_deliveries / ad_events / ad_repeat_windows / ad_estimated_usage_ledger | 순환·배달/서명·최초 판정/원응답·반복 창·인정 예상 원장을 같은 MongoDB 트랜잭션으로 확정 |
| 정책2 | ad_budget_states / ad_daily_metrics | 당시 예산 버전/발생일별 검증·최초 소진 cutoff/내부 log_record와 원장 합 기반5분 통계 교체 |

`ads`의 선택 예산 쌍 daily_budget_tokens/total_budget_tokens는 양의 BSON int64이며 서버 UUID budget_version은 실변경에만 갱신합니다. 예산 미설정 또는 검증 상태가 없는 광고는 공개 부적격입니다. 실제 금액 기본값은 없습니다. 예산 증액은 새 버전 검증을 거쳐 제공하며 수동 paused를 해제하지 않습니다.

배달에는 display_expires_at=min(발급+30분,게시 종료)과 event_expires_at=표시 마감+300초를 따로 저장하고3초 표시 lease/원본90일 보관과 구분합니다. 소재(title/asset/link) 변경 뒤 이전 배달 표시는 막되 변경 이전 당시 상태로 발생/보고를 검사하고 최초 응답을 보존합니다. 수신 시 현재 광고나 새 예산 버전으로 과거 판정을 덮지 않습니다.

5분 작업은 광고 단위 잠금과 트랜잭션 안에서 인정 예상 원장의 발생일KST·광고/위치 합을 재계산하여 ad_daily_metrics를 교체합니다. 지연 보고는 과거 날짜에 반영하고 재실행은 누적 증분을 중복 더하지 않습니다. 관리 응답은 as_of/coverage/aggregation_status와 오늘·누적 범위를 반환합니다. 일일KST 정렬은 기존 발생일 기준과 맞춘 개발 기준이며 자정 delivery 단축은 기본 미사용입니다.

같은 작업의 예산 검증에서 해당 일일/전체 합이 한도 이상이면 예산 버전/일자별 최초 daily_blocked_at·버전 전체 total_blocked_at을 보존합니다. 현재 광고의 budget_blocked_at과 검증 상태·최초 소진 log_record를 같은 광고 트랜잭션으로 저장합니다. 소진 확인 이전 발생은300초 내 유효 지연 보고/초과도 인정하고 확인 시각부터는 제외합니다. 요청마다 원장을 합산하거나23/20토큰을 예약하지 않습니다. 공개 경로는 검증 상태를 확인하여 신규/재확인/이미지를 차단하며 상태가300초 넘게 오래되면503 기술 장애로 처리합니다. 캠페인 자동 종료는 예산 소진 확인/게시기간 종료이고 검증 장애나30분 배달 만료는 추가 종료 조건이 아닙니다.

스키마는 replica set의 unique/validator와 CAS를 함께 검증합니다. apply_ads_policy_schema는 기본 dry-run·--apply 로컬 개발 DB 제한, refresh_ads_policy는 단발/--watch 시작 간격300초, check_ads_logs는 내장 로그의 건수/표본 hash를 읽기 점검합니다. 운영 watch 상주·공유 인증·AWS·브라우저 통합은 미실행입니다. 관리자 화면이나 ADS04 수령 원문을 변경하는 계약은 아닙니다. 보관90/365일은 유지하고 미승인 asset 정리 기간/실금액/실제 과금은 확정하지 않습니다.

## 4. 환경/보관/검증 인계
