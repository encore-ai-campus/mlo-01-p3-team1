# 3차 저장소 경계와 발행 계약

- 작성일: 2026-10-14
- 수정일: 2026-10-14
- 사용자 결정: 새 음악 담당 문서를 우선하여 음악은RDB4개, 로그/공통 상태는PostgreSQL, 광고는MongoDB입니다. 음악 원본/백업은로컬/S3 보관 가능하며 3차 음원 파일은 저장하지 않습니다.
- 상태: 음악 S3 기준 저장 결정을 새 수령 문서의RDB4개로 정정한 설계입니다. 설치/적재/발행/이전은 미실행입니다.

## 2026-10-14 광고 관리 간소화 적용

사용자가 제공한 [간소화 원문](../handoff/ads/04_광고_관리_간소화_인수인계서.md)과 [통합·추가 인계](../handoff/ads/05_광고_간소화_통합과_추가_인계.md)를 현행 광고 기준으로 적용합니다. 첫 관리 단계는 ads/ad_assets/ad_admin_changes 세 컬렉션·MongoDB 이미지 Binary·관리 감사/멱등 응답 통합입니다. 3차는 카페 전용이며 관리자/사용자 업종 선택·태그 입력·업종별 매칭은 제공하지 않습니다. 해당 확장은4차로 분리합니다. 공개 제공/측정과 토큰/주기 통계/예산은 다음 구현 단계이며 전체3차 필수 범위와 기존 태스크 ID/직접 선행은 유지합니다. 이하 기존 확장 저장 표는 후속 검토 자료이며 지금 일괄 생성하지 않습니다.

3차는 카페 광고만 운영하고 위치·일정·paused·소재·예산 자격을 충족한 후보에서 높은 priority·위치별 동률 순환을 적용합니다. 업종/태그가 제공·측정의 전제가 아니며 최초 guest 발급·추천 미요청 집계·단가8/5/클릭추가15·중복/지연/보관은 유지합니다. 미연결 지표는 연동 대기, 실제 통계는 주기 집계하며 예산 제공 제어와 구분합니다. 첫 관리 로그는 ad_admin_changes 내부 log_relay로 전달합니다. 업종별 입력/태그/매칭/순환은4차 인계에서 정하고3차 API/DB/화면/검증의 선행 조건으로 넣지 않습니다.

## 2026-10-14 음악 담당 수령 문서 우선 적용

[음악 통합 계약](./3차_음악_정책_통합_계약.md)을 적용합니다. 추천·표시18개 + 검수 보조1개·RDB4개·원본 변환·날씨50:45:5/전체75:25·장르/speed 필수 필터·사이클 고정·PTY6/7·시간176~184분을 기준으로 합니다. 새 자료의 미정은 유지하며 수동 전용16개·음악 S3 기준 저장·자동25% 단축과 동시에 적용하지 않습니다.

## 1. 기준 저장소

| 영역 | 저장/처리 경계 | 담당 |
|---|---|---|
| 음악 | RDB music_track/music_album/music_tag/track_tag·추천/표시18개+검수 보조1개·불변 카탈로그. 원본/백업/내보내기는로컬/S3 | C/INF·B저장연결·PL검수 |
| 로그/피드백 | PostgreSQL의 원본 행동/평가·당시 조건/곡·정제/집계/관리 조회·HTTP/진단/외부호출 로그 | B·C당시곡·A날씨·INF |
| 공통 업무 상태 | PostgreSQL의계정/세션/guest·작업/lease·결과/제외/평가/승인·정책/현재카탈로그 포인터·outbox | B/C/INF |
| 광고 | MongoDB의 광고/소재메타데이터·delivery/최초판정·반복창/순환·집계/예상원장/관리이력·로그outbox | B/INF·C공개배너 |
| 광고 로그 | PostgreSQL 사본/진단, MongoDB 광고업무와 event_id로 연결 | B/INF |
| 날씨 | 기존Collector→Kafka→Spark→날씨MongoDB→Elasticsearch, 원문로컬+S3 유지 | A/INF |

광고 MongoDB와 날씨 MongoDB는 논리DB/권한/정리를 분리합니다. 음악 RDB 선택은 광고 이미지의 저장 방식을 대신 확정하지 않습니다. 음악/로그의 저장 변경은 Kafka/Spark 처리 자체를 삭제하는 결정이 아니며 **피드백의 최종 원본·정제·집계 저장은 PostgreSQL로 바꿉니다.** Bronze/Silver/Gold는 논리 처리 단계명으로 유지할 수 있으나 현행 피드백에 Delta 물리 테이블/체크포인트를 필수로 요구하지 않습니다.

## 2. 음악 RDB4개와 불변 카탈로그

음악 담당의 [테이블 설계](../handoff/music/테이블_구조_설계.md)를 우선합니다. music_track·music_album·music_tag·track_tag가 곡 기본4개입니다. 추천·표시18개와 instrumental_review_value를 구분하고 FK/UNIQUE·활성/승인 연결·곡당 한 행 집계를 적용합니다. DB 제품/물리DDL/접속은 별도 환경 검증이며 공통 PostgreSQL 선택으로 자동 확정하지 않습니다.

1. 원본CSV는 로컬/S3 보관 가능하며 source/schema/version·해시·원본 행/고유 곡 수·오류를 기록합니다. 원본과 결과19개 입력을 구분하고 변환은 원본에서만 수행합니다.
2. 곡/앨범/태그/연결 적재는 음악RDB의 트랜잭션·FK/UNIQUE로 검사합니다. 일반 upsert는 확정 검수값을 보존하고 검수 변경은 별도 작업으로 수행합니다.
3. 태그를 종류별로 먼저 집계해 music_recommendation_view에서 곡당 한 행·18개·genre_group_codes를 제공합니다. 활성/approved 연결만 공개 조회에 사용하고 원본 연결은 보존합니다.
4. 검증된 조회 결과를 catalog_version별 불변 스냅샷으로 고정합니다. 정확한 물리 발행/내보내기 형식·manifest·접속은 C/B/INF가 확정합니다. S3는 보관/내보내기 수단일 수 있으며 음악 기준 저장을 대신하지 않습니다.
5. 검증/전체 읽기 완료 후 공통 PostgreSQL의 catalog_snapshot/READY 포인터를 전환합니다. 음악RDB와 업무DB가 다르면 두 DB의 원자 동시쓰기를 가정하지 않고 완료된 불변 자료를 먼저 준비합니다. 실패 시 현재 정상 포인터를 보존합니다.
6. 작업은 카탈로그/정책/사이클/당시 값·해시를 고정하고 검증된 조회 모델로 규칙/Gemini에 같은 적격 목록을 제공합니다. 사용자 요청마다 Spark/원본 전체를 스캔하거나 최신 테이블로 과거 스냅샷을 바꾸지 않습니다.

검수 이력·카탈로그 버전/발행 감사·결과/제외/평가/정책은 음악 기본4개와 별도 운영 자료입니다. 정확한 제품/DDL·물리 경계·백업/보관은 인계 사항입니다. 3차 음원 파일·직접 재생·Spotify API 필수 연동은 추가하지 않습니다.

## 3. PostgreSQL 로그·피드백의 원자성/재처리

결과/제외/평가/승인 상태와 feedback_event·당시 context/곡·outbox·멱등 응답은 기존 PostgreSQL 트랜잭션으로 유지합니다. Kafka relay는 같은 event_id를 발행하고 Spark는 원본/정제/집계를 PostgreSQL에 멱등 반영합니다. PostgreSQL 원본 단계는 source_domain·topic/partition/offset·payload·수신/처리 시각·is_test를 기록하며 offset 적재 대조/경보를 유지합니다.

온라인 업무 feedback_event와 파이프라인 원본 기록의 역할을 구분하고 같은 DB에 있다는 이유로 발행/수신 확인을 생략하지 않습니다. 원본 단계의 고유 키는 stream/partition/offset 또는 안정적 배달 ID, 정제는 event_id·대상 revision입니다. 평가 취소/역순/중복·선택 태그와 곡 태그·당시 값·보관 중 스냅샷을 유지합니다. PostgreSQL 원본/정제/집계는 별도 스키마/권한/인덱스·pool/timeout으로 조율합니다.

재처리는 Kafka 보관 범위 또는 확인된 PostgreSQL 원본에서 별도 출력/실행 ID로 수행하고 최초 ID/판정·revision을 보존해 결과를 대조합니다. Spark checkpoint는 실행 상태이며 로그 기준 저장소가 아닙니다. Kafka와 PostgreSQL 양쪽 원본이 없는 구간은 복구 불가입니다. 과거 Delta 제안이나 옛 검증 기록을 현행 구현 완료로 표시하지 않습니다.

광고 업무 로그는 첫 관리 단계의 ad_admin_changes 내부 log_relay에서 PostgreSQL로 멱등 발행합니다. 후속 측정 로그의 보조 구조는 해당 단계에서 결정하며 별도 outbox 컬렉션을 지금 필수 생성하지 않습니다. 두 DB의 원자 동시 쓰기를 가정하지 않으며 광고 집계의 기준 원본은 MongoDB입니다. 상세 컬렉션/원자성/보관은 [ADS 저장 계약](../handoff/ads/02_광고_MongoDB_저장과_로그_연결.md)을 따릅니다.

## 4. 환경/보관/검증 인계

INF는 MUSIC_DATABASE_URL·DB제품/음악schema·DDL/FK/키생성·트랜잭션·불변카탈로그발행/조회·백업, 선택한원본/내보내기S3의bucket/key·권한·해시/암호화, DATABASE_URL/로그 namespace·인덱스/보관, ADS_MONGODB_URI/DATABASE·replica set/권한/백업을 제공합니다. 실제 비밀값은 문서에 넣지 않습니다.

음악RDB 적재/불변 카탈로그 검증 후 포인터 전환 전 종료·포인터 커밋 응답 유실·이전 버전 캐시·동시 발행·객체 누락/해시 불일치, PostgreSQL 원본 누락/중복/역순/재처리, MongoDB 커밋/로그 relay 부분 실패를 고정 자료로 검증합니다. 음악 객체·결과/스냅샷·로그의 보관 기간은 미정으로 유지하고 광고90/365일을 다른 도메인으로 확대하지 않습니다.

받은 [AWS 원문](../handoff/infra/AWS_인프라_구축_계획서.md)과 로컬 원문은 수령 자료로 보존합니다. 원문의 음악/Delta 설명은 최신 수령 음악 규격과 로그 계약을 덮지 않으며 원문과 실제 구성의 차이는 [인프라 인계](../handoff/infra/README.md)에 기록합니다. 기존 태스크 ID/직접 선행 관계·추천 정책·사용자 기능은 유지합니다.
