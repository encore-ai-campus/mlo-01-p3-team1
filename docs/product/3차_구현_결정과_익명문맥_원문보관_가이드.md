## 최신 결정 — 규칙 기본 추천과 Gemini 보조 재설정

### 3차 국가·언어 제외·ON/OFF 점수·신규 곡 기준 — 2026-10-16 갱신

3차에는 국가·언어 설정/검수/필터/가점/관리 입력/피드백 필드를 제공하지 않습니다. 음악18개 추천·표시 필드와 원본 점수 특성을 사용하고 보컬 검수·mood테마·genre·speed만 현재 기능에 연결합니다. 기본/재설정 요청은 국가·언어 관련 필드를 허용하지 않으며 이전 언어 선택을 상속하거나 숨겨 적용하지 않습니다. 별도 후속 단계 채택은 미정입니다.

추천 점수는 모드별로 분리합니다. ON은 날씨 5종×2패턴의 적격 W≥75를 먼저 적용한 뒤 활성 선호와 75:25를 적용하고, OFF는 날씨에 독립적인 P_OFF(장르·energy·mode·speed 40:40:5:15)를 사용합니다. 원본 정밀도·필터·NULL·장르 구성은 최신 후보 산출 가이드를 따릅니다.

새 결과는 부모 전체 고유 곡 수N의20% 내림값 이상인 신규 곡을 포함하면 인정합니다: required_new_count=max(1,N//5), actual_new_count=len(result_ids-parent_ids). 기존 곡 제거는 필수 조건이 아니며 추가만으로도 통과할 수 있습니다. 부모 분모는 제외 후에도 유지하고 순서/설명 변경·기준 미달은 실패 안내와 부모 보존입니다. 등록/검수·무보컬·제외·중복·모드별 필터·시간 검증(ON에만 유효 예보)은 별도로 모두 통과해야 합니다.


### 곡별 반응·선곡표 만족도 — 2026-10-13 추가

3차 공개 추천에 곡별 [좋아요]/[싫어요]와 선곡표 전체의 별점 1~5점 만족도 평가를 추가합니다. 곡 반응은 LIKE/DISLIKE/미평가(null)의 세 상태이며 같은 버튼 재클릭은 해제, 반대 버튼은 전환합니다. 별점은 곡 목록 바깥의 [이 선곡표 만족도] 영역에 정수 1~5점으로 선택하고 [평가 취소]로 해제합니다. 둘 다 선택 입력·초기 미평가이며 비로그인 본인 결과에서 이용합니다. 곡 반응과 별점은 실제 결과 버전에 귀속하고 새 결과로 복사하지 않습니다. 곡 제외·승인과 별개이며 자동 추천/제외/승인·점수 변경·Gemini 호출을 유발하지 않습니다. 저장/취소·당시 조건/곡·revision·outbox·집계·검증은 구현 설계도 6-9절을 따릅니다. 실제 UI/API 구현 완료를 뜻하지 않습니다.


기본 추천은 음악18개 추천·표시 필드와 원본 정밀도 점수 특성을 사용해 ON/OFF 모드별 규칙·정수 시간 조합으로 생성합니다. Gemini는 사용자의 명시 재설정에만 같은 모드의 적격 RDB 목록에서 제안합니다. 국가·언어 기능은 제외하며 이전 16개/수동 energy W/음향3개 점수는 현행 추천식이 아닙니다.

[현행 Gemini API 추천 설계](./카페_음악_서비스_3차_Gemini_API_추천_설계.md). 규칙 가이드는 현행으로 복원하고 보관본은 이력으로 유지합니다. Gemini 재설정 실패 시 부모 결과/초안을 유지하고 자동 규칙 재생성으로 바꾸지 않습니다. 실제 API 호출·과금·DB 변경·배포는 이번 문서 작업에서 하지 않습니다.

## 2. 익명 문맥과 추천 계열

익명 문맥은 로그인하지 않은 브라우저가 자기 추천 작업·결과·제외 초안을 제어하는 서버 소유 단위입니다. 회원·사람·카페 ID가 아니며 IP를 소유 기준으로 사용하지 않습니다.

```text
브라우저 A → guest 쿠키 → 내부 guest_id A
                              ├─ family 1: 원본 결과 → 재생성 결과, 제외 초안 유지
                              └─ family 2: 독립 새 추천, 빈 제외 초안
브라우저 B → 다른 guest 쿠키 → A의 결과/초안 접근 불가
```

### 2.1. 발급과 접근 검사

1. 최초 추천 요청에서 유효한 쿠키가 없으면 서버가 예측하기 어려운 접근 토큰을 발급합니다. 공개 지역/날씨/광고 조회만으로 문맥 발급을 강제할 필요는 없습니다.
2. 토큰은 브라우저 쿠키로 전달하고 서버에는 내부 guest_id와 토큰 검증 자료를 연결합니다. 원문 토큰을 이벤트·로그·URL·localStorage에 기록하지 않습니다.
3. 실서비스 HTTPS에서는 Secure·HttpOnly·SameSite를 적용하고 변경 API의 CSRF/Origin을 검사합니다. 로컬 HTTP의 개발 설정은 운영 쿠키 설정과 분리합니다.
4. 작업 등록·조회·결과 조회·제외 GET/PUT·재생성·승인에서 문맥 유효성·소유·상태를 검사합니다. 결과 ID만 안다고 접근시키지 않습니다.
5. 쿠키가 유지되면 새로고침/재접속에서도 보관 중인 본인 자료를 조회할 수 있습니다. 최근 결과를 자동으로 다시 여는 화면 복원은 별도 설정이며 소유 토큰에 화면 정보를 합치지 않습니다.

### 2.2. 만료와 보관

문맥 만료, 결과 보관, 제외 초안 보관, 피드백 이력 보관은 서로 다른 정책입니다. 같은 기간으로 임의 고정하지 않습니다. 쿠키 삭제·다른 기기·시크릿 창에서는 이전 소유 복원을 보장하지 않습니다.

접근이 만료되면 새 문맥으로 시작하고 과거 결과를 자동 이관하지 않습니다. 만료됐다고 관리자용 당시 피드백 스냅샷을 무조건 연쇄 삭제하지 않습니다. 활성 초안의 취소에 필요한 원래 제외 이벤트·곡 스냅샷은 초안 유효기간까지 조회 가능해야 합니다.

미정 설정은 guest 만료, 결과/초안 보관, 최근 결과 복원, 요청/동시 생성 한도입니다. 개발 설정으로 시작하되 적용값·단위·버전을 기록합니다. 로그인만으로 익명 결과를 계정 이력에 편입하지 않습니다.

## 3. 로컬·S3 원문 보관

원문은 기상청 응답의 정제 전 바이트입니다. 로컬과 S3 두 사본을 보존하지만 전체 서비스의 이중화나 자동 장애 전환을 뜻하지 않습니다.

```text
응답 수신 → 요청/시각/출처 확인 → 원문 해시 계산
         → 로컬 임시 파일 작성 → 완료 파일로 전환
         → Kafka 발행/정규화 경로 연결
         → 내구성 있는 S3 업로드 작업 → 완료/실패 상태 기록·재시도
```

로컬 저장 완료 후 정규화는 진행하고 S3는 재시도 가능한 후속 작업으로 처리하는 초기 구현안을 사용합니다. S3 실패를 숨기지 않으며 양쪽 성공 전에는 두 곳 보관 완료로 표시하지 않습니다. 로컬 저장 실패는 원문 보관 성공으로 처리하지 않습니다.

### 3.1. 식별과 저장 메타데이터

| 필드 | 의미 |
|---|---|
| raw_id·source_hash | 원문 식별, SHA256 원문 해시. 동일 응답 재전송 식별 |
| source/category·요청 정보 | API 출처·항목·회차. 인증키는 제외 |
| issued_at/target_at/received_at | 발표·대상·수신 시각 |
| local_path·local_status | 완성 파일 위치와 보관 상태 |
| s3_bucket/key·s3_status | S3 사본 위치와 PENDING/UPLOADING/COMPLETED/FAILED 상태 |
| attempt_count·last_error·next_retry_at | 업로드 재시도/경보 근거 |
| raw_size·compression | 원문 크기·gzip 여부 |

source_hash는 압축 전 원문 바이트 기준입니다. gzip을 해제하면 원래 응답이 복원돼야 합니다. S3 ETag를 SHA256과 동일하다고 가정하지 않고 기록된 원문 해시로 무결성을 확인합니다.

S3 키는 출처·날짜·회차/대상·해시 등을 포함해 같은 원문에 안정적으로 정합니다. 동일 키 재시도는 같은 내용에만 사용하고 발표가 같아도 원문이 바뀌면 새 해시/사본을 남깁니다. 버킷 접근 자격증명은 환경 설정으로 제공하며 공유 문서에 저장하지 않습니다.

### 3.2. 업로드 실패·재처리·삭제

업로드 큐/메타데이터는 프로세스 재시작 후 미완료 작업을 다시 찾을 수 있어야 합니다. 업로드 직후 응답 유실도 객체와 해시를 확인해 멱등하게 완료 처리합니다. 로컬/객체의 존재 확인만으로 다른 내용의 파일을 정상 사본으로 인정하지 않습니다.

재처리는 유효한 로컬 사본을 우선 읽고 없으면 S3에서 읽습니다. 반대쪽 접근 실패 시 남은 유효 사본을 사용할 수 있지만 두 곳 모두 없으면 복구 불가로 기록합니다. DB·Kafka·Delta·MongoDB·Elasticsearch 복구는 원문 파일 복구와 별개입니다.

로컬 정리 전 S3 COMPLETED와 무결성을 확인합니다. 장기 원문 보존용 S3의 삭제/보관 정책은 별도로 정합니다. 재시도 대기 파일·재처리 참조·보관 중인 이력 연결을 끊는 정리를 하지 않습니다.

## 4. 후보군 확장과 관리자 회수

### 4.1. 기본 후보군 확장과 Gemini 입력 목록

기본은 기존 규칙 점수·정수 조합 탐색을 유지합니다. 작은 적격 후보군부터 상한까지 확장하고 상위 시간 구간을 충분히 확인하지 못하면 최적성 미확인을 기록합니다. 500→1,000→2,000→5,000은 설명용 예시이며 실제 값은 미정입니다.

Gemini는 결과 불만족의 명시 재설정에서만 호출합니다. ON/OFF별 적격 RDB 후보를 제공하고 부모 결과·모드·선택·제외를 고정합니다. ON에만 유효 예보/날씨 점수를 요구합니다. 실패하면 부모를 보존하며 규칙 가이드와 보조 재설정 설계를 함께 적용합니다.

### 4.2. 관리자 발급과 회수

초기화 명령으로 관리자 계정을 만들고 역할·권한을 초기 배정합니다. 초기화 재실행이 기존 비밀번호/권한을 조용히 덮어쓰거나 같은 계정을 중복 생성하지 않도록 합니다. 비밀번호를 공유 파일·명령 로그에 기록하지 않습니다.

회수는 is_active=false 같은 비활성 상태와 기존 세션 무효화를 함께 적용합니다. 신규 로그인과 모든 관리자 API에서 활성 상태·권한을 검사합니다. 작성자 account_id와 검수·광고·피드백 조회 이력 연결은 보존하며 회수를 물리 삭제로 구현하지 않습니다. 계정 전체 비활성화와 일부 권한 회수는 구분합니다.

## 5. 날씨 유효성과 유형 매핑

PTY4/5는 비, PTY7은 눈으로 정규화합니다. PTY2/6은 비·눈 양쪽 적격 풀의 교집합을 사용합니다. 원본/표시 코드는 보존하고 ON의 유효 날씨 분류·시각을 검사합니다. OFF 추천은 날씨 상태에 의존하지 않습니다.

발표 최신성, 추천 대상 시각 확보, 분류에 필요한 항목의 valid 여부를 각각 검사합니다. 강수 없는 구간은 유효 SKY가 필요하고 유효 PTY로 강수 유형이 정해진 구간의 SKY 누락을 동일하게 취급하지 않습니다. 화면용 항목 누락을 음악 필수값 누락과 구분합니다.

앞 180분의 필수 예보 누락/만료는 새 생성 차단, 실제 초과 결과는 total_ms까지 확인합니다. 뒤쪽 6시간 조회만 일부 누락됐으면 유효 추천 구간을 막지 않습니다. 구체 만료값·구간 경계·수집 제공 지연·재시도는 구현 설정으로 기록하며 오래된 정상값으로 최신 결측을 덮지 않습니다.
